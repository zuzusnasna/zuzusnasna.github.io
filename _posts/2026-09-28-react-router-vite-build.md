React 프로젝트에서는 여러 화면을 하나의 애플리케이션에서 관리해야 하기 때문에 라우팅과 빌드 구조를 함께 이해할 필요가 있었다.

## Router

```jsx
<Routes>
  <Route path="/" element={<Home />} />
  <Route path="/login" element={<Login />} />
  <Route path="/rooms/:roomId" element={<Room />} />
</Routes>
```

URL에 따라 다른 컴포넌트를 렌더링할 수 있다.

## Vite

Vite는 개발 서버와 번들링 환경을 빠르게 구성할 수 있다.

```bash
npm run dev
npm run build
```

`dev`는 개발 서버에서 빠르게 확인하는 용도이고 `build`는 배포할 결과물을 만드는 과정이다.

## 실제 오류에서 배운 점

React 프로젝트에서 JSX 문법이 깨지거나 `node_modules`가 손상되면 애플리케이션 코드가 아니라 빌드 환경에서 오류가 발생할 수 있다. 이때는 오류가 발생한 레이어를 먼저 구분해야 한다.

## 배운 점

프론트엔드도 코드만 보는 것이 아니라 **소스 → 개발 서버 → 빌드 → 정적 파일 → 배포 서버**의 전체 흐름을 이해해야 문제를 빨리 찾을 수 있었다.

## 더 깊게 이해하기: 개발 서버와 배포 결과물은 다르다

Vite 개발 서버는 모듈을 빠르게 제공하고 개발 중 편의를 제공하지만, 운영 배포에서는 빌드된 정적 파일과 실제 배포 경로가 중요해진다. 프로젝트가 도메인의 루트가 아니라 하위 경로에 배포되면 asset 경로와 라우터의 기준 경로가 맞지 않아 새로고침 시 404가 발생할 수 있다.

React Router를 쓰는 SPA는 브라우저에서 경로를 해석하므로, 사용자가 `/rooms/1` 같은 URL로 직접 접근했을 때 웹 서버도 해당 요청을 애플리케이션 진입점으로 돌려줘야 한다. 개발 서버에서는 자동으로 처리되지만 Nginx나 정적 호스팅 환경에서는 별도 설정이 필요할 수 있다.

### 배포 전 확인
- `vite.config`의 `base` 값과 실제 배포 경로가 일치하는가?
- 빌드 결과의 JS·CSS 경로가 배포된 위치를 가리키는가?
- 내부 이동뿐 아니라 URL 직접 입력과 새로고침도 동작하는가?
- API 요청 경로와 정적 파일 경로를 혼동하지 않았는가?

개발 환경에서 보이는 화면만 확인하지 말고, 실제 빌드 산출물을 목표 경로에 배치해 테스트하는 것이 배포 문제를 줄인다.
