인증 방식을 공부하면서 세션, JWT, OAuth2를 모두 로그인이라고 묶으면 오히려 헷갈렸다.

## Session

서버가 인증 상태를 저장하고 클라이언트는 세션 식별자를 전달한다.

```text
로그인
 ↓
서버 세션 생성
 ↓
Session ID
 ↓
이후 요청에서 인증 확인
```

## JWT

인증 정보를 토큰에 담아 클라이언트가 전달하는 방식이다. 서버가 매 요청마다 토큰의 서명과 내용을 검증한다.

## OAuth2

Google, Naver, Kakao 같은 외부 서비스가 사용자의 인증을 수행하고 우리 서비스가 그 결과를 이용하는 방식이다.

```text
우리 서비스
   ↓
OAuth Provider
   ↓
인증 성공
   ↓
Callback
   ↓
우리 서비스의 사용자 처리
```

## 중요한 구분

- Session / JWT → 인증 상태를 어떻게 유지하고 전달할 것인가
- OAuth2 → 외부 인증 제공자와 어떻게 인증을 연동할 것인가

## 배운 점

기술 이름보다 **인증 주체와 인증 상태가 어디에 존재하는지**를 먼저 보면 각 방식의 차이가 명확해졌다.

## 더 깊게 이해하기: 로그인 성공 이후에도 보안은 계속된다

OAuth 2.0은 권한 위임을 위한 프레임워크이고, OpenID Connect는 그 위에 사용자 인증 정보를 표준화해 제공한다. JWT는 토큰 형식이지 로그인 프로토콜 자체가 아니다. 이 셋을 같은 개념으로 취급하면 인증 흐름과 토큰 검증 책임이 섞이기 쉽다.

JWT를 받았다는 이유만으로 신뢰해서는 안 된다. 서버는 서명, 만료 시간, 발급자와 대상 등 서비스에서 요구하는 클레임을 검증해야 한다. 또한 토큰을 어디에 저장할지, 탈취되었을 때 어떻게 만료시키거나 재발급을 통제할지도 함께 설계해야 한다.

### 흐름을 직접 그려 보기
1. 사용자가 외부 인증 제공자에게 인증한다.
2. 콜백에서 state 등 요청 위조 방지 값을 확인한다.
3. 서버가 검증된 사용자 식별 정보를 내부 계정과 연결한다.
4. 서비스가 선택한 세션 또는 토큰 방식으로 이후 요청을 인증한다.
5. 로그아웃·만료·계정 연결 해제 상황을 별도로 처리한다.

외부 제공자의 사용자 ID와 서비스 내부 회원 ID를 구분하고, 비밀번호나 access token을 로그에 남기지 않는 것이 기본이다.
