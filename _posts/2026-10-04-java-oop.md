Java를 배우면서 가장 중요한 전환점은 절차적으로 코드를 작성하는 것에서 **객체의 책임을 나누는 것**으로 생각을 바꾸는 과정이었다.

## 클래스와 객체

클래스는 객체를 만들기 위한 설계이고 객체는 실제로 생성된 인스턴스다.

```java
class Member {
    private String name;

    public Member(String name) {
        this.name = name;
    }

    public void hello() {
        System.out.println(name + "님 안녕하세요.");
    }
}
```

## 캡슐화

필드를 `private`으로 감추고 메서드를 통해 필요한 동작만 제공한다. 데이터의 변경 규칙을 객체 내부에 둘 수 있다는 것이 핵심이었다.

## 상속과 다형성

부모 타입으로 자식 객체를 다루면 같은 호출을 유지하면서 실제 구현을 다르게 만들 수 있다.

```java
Animal animal = new Dog();
animal.sound();
```

## 인터페이스

인터페이스는 구현 방법보다 기능에 대한 계약을 정의한다. 구현체가 여러 개일 때 사용하는 쪽의 결합도를 낮출 수 있다.

## 정리

객체지향의 핵심은 단순히 `class`를 만드는 것이 아니라 **각 객체가 어떤 책임을 가지고 협력할 것인지 결정하는 것**이라고 정리했다.

## 더 깊게 이해하기: 객체지향은 클래스를 많이 만드는 기술이 아니다

객체지향 설계에서 중요한 것은 데이터와 그 데이터에 적용되는 규칙을 함께 관리하고, 변경이 필요한 이유를 분리하는 것이다. 모든 명사마다 클래스를 만들면 오히려 의존성이 늘어난다. 반대로 여러 책임이 한 클래스에 모이면 작은 요구사항 변경도 넓은 수정으로 이어진다.

캡슐화는 필드를 private으로 바꾸는 것에서 끝나지 않는다. 객체가 허용된 상태만 갖도록 변경 규칙을 메서드 안에 두는 것이 핵심이다. 상속은 코드 재사용을 위해 무조건 사용하는 기능이 아니며, 하위 타입이 상위 타입의 약속을 지킬 수 있는지 확인해야 한다.

### 설계 검토 질문
- 객체가 스스로 지켜야 하는 불변 조건을 메서드로 표현했는가?
- 한 클래스가 여러 이유로 변경되고 있지 않은가?
- 상속 대신 조합이나 인터페이스로 의존성을 분리할 수 있는가?
- 테스트가 내부 구현이 아니라 외부에서 관찰되는 동작을 검증하는가?

좋은 객체 모델은 클래스 수가 많아서가 아니라 변경의 영향 범위가 작고 규칙이 한 곳에서 이해될 때 만들어진다.
