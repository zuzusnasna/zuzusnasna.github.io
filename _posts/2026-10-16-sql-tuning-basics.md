SQL 성능 문제를 해결할 때 가장 먼저 쿼리를 고치는 것보다 **왜 느린지 확인하는 과정**이 중요하다는 것을 배웠다.

## 확인 순서

1. 실행되는 SQL 확인
2. 조건과 JOIN 구조 확인
3. 실행 계획 확인
4. 인덱스 사용 여부 확인
5. 실제 데이터 양과 선택도 확인
6. 변경 후 다시 측정

```sql
EXPLAIN PLAN FOR
SELECT *
FROM employee
WHERE department_id = 10;

SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY);
```

## 중요한 점

인덱스가 있다고 무조건 빨라지는 것은 아니다. 데이터 분포와 조건에 따라 Full Table Scan이 더 적절할 수도 있다.

튜닝은 추측으로 끝내는 작업이 아니라 **측정 → 원인 확인 → 변경 → 재측정**의 반복이라고 정리했다.

## 더 깊게 이해하기: 튜닝은 SQL을 짧게 쓰는 작업이 아니다

SQL 성능은 문장 길이보다 실행 계획과 데이터 분포에 영향을 받는다. 먼저 실제 실행 계획에서 접근 경로, 조인 순서, 예상 행 수를 확인하고, 어떤 연산이 많은 데이터를 읽거나 정렬하는지 살펴야 한다. 인덱스를 추가하면 조회가 빨라질 수 있지만 쓰기 비용과 저장 공간이 증가하므로 모든 컬럼에 인덱스를 만드는 방식은 적절하지 않다.

같은 SQL도 데이터 건수와 통계 정보, 바인드 변수의 값에 따라 다른 비용을 보일 수 있다. 실행 시간을 한 번 측정한 값만으로 결론 내리지 말고, 동일한 조건과 충분한 반복으로 비교해야 한다.

### 튜닝 절차
1. 느린 SQL과 재현 조건을 고정한다.
2. 실행 계획과 실제 처리 행 수를 비교한다.
3. 불필요한 전체 스캔, 정렬, 반복 조회를 찾는다.
4. 인덱스 또는 쿼리 구조를 변경한다.
5. 결과의 정확성과 성능을 같은 조건에서 재검증한다.

튜닝의 첫 단계는 변경이 아니라 관측이다. 무엇이 비용을 만드는지 설명할 수 있어야 개선 방향도 설득력을 갖는다.
