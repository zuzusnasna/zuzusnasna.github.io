Cursor를 공부하면서 단순히 문법을 외우기보다 **여러 행을 하나씩 처리해야 하는 업무**를 떠올리는 것이 이해에 도움이 됐다.

## 왜 필요한가

SQL은 여러 행을 한 번에 처리하는 데 강하지만, 각 행마다 서로 다른 계산이나 조건을 적용해야 하는 경우가 있다.

예를 들어 직원별 급여 형태가 정규직, 시간제, 일급제로 나뉘고 각각 계산 방식이 다르다면 행 단위 처리가 필요할 수 있다.

```sql
FOR emp IN (
    SELECT employee_id, salary_type, salary
    FROM employee
) LOOP
    IF emp.salary_type = 'FULL_TIME' THEN
        -- 정규직 계산
        NULL;
    ELSIF emp.salary_type = 'PART_TIME' THEN
        -- 시간제 계산
        NULL;
    END IF;
END LOOP;
```

## 프로젝트에 적용한다면

휴대폰 사용량, 카드 사용 내역, 배달 주문 이력처럼 고객별 데이터를 모아서 등급을 갱신하는 작업에도 행 단위 처리가 필요할 수 있다.

다만 모든 데이터를 Cursor로 처리하는 것이 좋은 것은 아니다. 가능한 경우 집합 연산 SQL이 더 효율적일 수 있기 때문에 **정말 행 단위 업무가 필요한지 먼저 판단**해야 한다.

## 더 깊게 이해하기: 업무 시나리오를 행 단위 처리로 바꾸기

커서 기반 업무를 설계할 때는 먼저 처리 대상 집합을 명확히 해야 한다. 예를 들어 특정 기간의 거래를 고객별로 집계해 등급을 갱신한다면, 처리 대상 고객을 정하는 SELECT와 고객별로 적용할 규칙, 결과 기록을 분리해 생각할 수 있다. 가능하면 GROUP BY와 UPDATE를 이용한 집합 연산으로 해결하고, 고객별 분기나 외부 처리처럼 행 단위 절차가 필요한 경우 커서를 사용한다.

대상 데이터가 실행 중 계속 바뀔 수 있다면 어느 시점의 데이터를 기준으로 처리할지도 결정해야 한다. 또한 중간에 실패했을 때 처음부터 다시 실행할지, 실패한 행만 재처리할지에 따라 이력 테이블과 상태 관리가 달라진다.

### 시나리오 설계 체크리스트
- 처리 대상과 제외 조건을 SQL로 명확히 정의했는가?
- 처리 건수, 성공 건수, 실패 건수를 기록하는가?
- 여러 번 실행해도 같은 데이터가 중복 반영되지 않는가?
- 트랜잭션 범위와 잠금 시간이 업무 규모에 맞는가?

업무 시나리오를 먼저 글과 데이터 흐름으로 정리하면 커서가 정말 필요한지, 어떤 상태를 기록해야 하는지 판단하기 쉬워진다.
