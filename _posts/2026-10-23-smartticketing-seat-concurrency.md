좌석 예매에서 가장 중요한 문제는 여러 사용자가 같은 좌석을 동시에 선택했을 때 **한 명만 성공해야 한다**는 것이었다.

## 처음 생각한 방법

처음에는 넓은 범위의 데이터를 잠그면 중복 예매를 막을 수 있다고 생각했다.

하지만 회차 전체나 구역 전체를 넓게 잠그면 서로 다른 좌석을 선택하는 사용자까지 기다리게 되어 동시성이 떨어진다.

## 개선 방향

```text
후보 좌석 조회
   ↓
회차 / 구역 기준 정리
   ↓
실제 선택 좌석 잠금
   ↓
재조회 및 유효성 확인
   ↓
선점 처리
```

핵심은 **필요한 데이터만 잠그는 것**이었다.

## 왜 synchronized로 끝내지 않았나

서버가 한 대라면 JVM 내부 동기화가 어느 정도 의미가 있지만 서버가 여러 인스턴스로 늘어나면 각 JVM의 lock은 공유되지 않는다.

따라서 DB의 트랜잭션과 잠금, Redis 같은 분산 환경의 제어 수단을 함께 고려해야 했다.

## 배운 점

동시성 제어는 단순히 잠금을 추가하는 문제가 아니라 **어디까지 잠글지, 트랜잭션을 얼마나 짧게 유지할지, 여러 서버에서 같은 규칙이 적용되는지**까지 설계해야 하는 문제였다.

## 더 깊게 이해하기: 동시성 제어는 불변 조건을 지키는 일이다

좌석 예매의 불변 조건은 동일한 회차의 동일 좌석을 유효하게 선점한 사용자가 둘 이상 존재하지 않는다는 것이다. 이 조건을 먼저 정의해야 어떤 잠금이나 제약이 필요한지 판단할 수 있다. 단순히 조회한 뒤 예약 상태를 바꾸면 두 요청이 모두 빈 좌석을 확인하고 각각 성공하는 경쟁 조건이 발생할 수 있다.

JVM의 `synchronized`는 같은 프로세스 안의 스레드만 조정하므로 다중 인스턴스 환경의 공통 제어 수단이 아니다. DB 잠금은 데이터 변경과 같은 트랜잭션 경계에서 사용할 수 있지만 잠금 범위와 대기 시간이 중요하다. Redis 기반 선점은 빠른 제어에 활용할 수 있지만 최종 데이터 정합성과 실패 시 보상 흐름을 별도로 설계해야 한다.

### 검증 시나리오
- 같은 좌석에 동시에 요청을 보내 한 건만 성공하는가?
- 서로 다른 좌석을 선택한 요청까지 불필요하게 직렬화되지 않는가?
- 트랜잭션 실패 후 선점 상태가 남지 않는가?
- 서버가 두 대일 때도 동일한 불변 조건이 유지되는가?
- DB 제약 조건이나 최종 재검증이 경쟁 조건을 방어하는가?

동시성 문제는 성공 응답 수뿐 아니라 DB에 저장된 최종 상태를 조회해 검증해야 한다.
