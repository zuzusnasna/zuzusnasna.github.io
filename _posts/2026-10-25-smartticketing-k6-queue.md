동시성 문제는 코드만 보고 해결됐다고 판단하기 어려워 실제로 여러 요청이 동시에 들어오는 상황을 만들어 검증했다.

## 테스트 목적

- 같은 좌석에 동시에 접근했을 때 중복 예매가 발생하지 않는가
- 대기열에서 같은 사용자가 중복 입장하지 않는가
- Redis 원자 연산이 경쟁 상황에서도 정확한가
- 응답 시간이 과도하게 증가하지 않는가

## k6

k6는 여러 가상 사용자가 동시에 HTTP 요청을 보내 부하 상황을 만들 수 있다.

```javascript
export const options = {
  vus: 5,
  duration: '1m'
};
```

단순히 성공 응답만 보는 것이 아니라 **DB 상태와 Redis 상태가 최종적으로 일치하는지**까지 확인해야 테스트 의미가 있다.

## 배운 점

성능 테스트는 숫자 하나를 얻는 작업이 아니라 **어떤 경쟁 상황을 만들고 무엇을 성공 조건으로 볼 것인지 정의하는 작업**이었다.

## 테스트 조건과 결과를 확인할 때

대기열 테스트에서는 단순히 요청을 많이 보내는 것보다 실제 사용 흐름을 재현하는 것이 중요하다. 동시에 대기 번호를 조회하는 요청, 입장 가능한 사용자의 확인, 만료 또는 취소 흐름이 섞이면 시스템이 어떤 부하를 받는지 더 현실적으로 관찰할 수 있다.

k6의 체크는 개별 응답의 조건을 확인하고, 임계값(threshold)은 테스트 전체의 성능 기준을 표현한다. 응답 코드가 모두 200이어도 p95 지연 시간이 기준을 넘을 수 있으므로 성공률과 지연 지표를 함께 본다. 반대로 부하 생성기가 병목이 되면 서버 성능을 정확히 측정하지 못할 수 있다.

### 결과를 해석할 때
- VU 수, 실행 시간, 요청률 등 부하 조건을 기록한다.
- 평균뿐 아니라 p95·p99와 실패율을 확인한다.
- 대기열의 정합성은 응답 코드가 아니라 중복 번호·누락·입장 순서로 검증한다.
- 테스트 전후 DB와 Redis 상태를 확인해 데이터가 기대대로 남았는지 확인한다.

재현 가능한 테스트 조건이 있어야 이후 코드 변경의 결과를 공정하게 비교할 수 있다.


## 구현하면서 같이 확인한 대기열 동작

SmartTicketing의 대기열은 Redis Sorted Set을 이용해 사용자의 대기 상태와 순서를 다루는 구조였다. Sorted Set의 score를 순서 기준으로 두면 특정 사용자의 순위는 앞에 있는 멤버 수를 기준으로 계산할 수 있다.

~~~text
대기열 진입
  ↓
Redis Sorted Set에 사용자 등록
  ↓
ZCOUNT로 앞 순서의 사용자 수 확인
  ↓
입장 가능 여부 확인
  ↓
좌석 선점 / 예매 진행
~~~

여기서 순위 조회와 입장 허용은 같은 문제가 아니다. 숫자로 대기 순서를 보여주는 것만으로는 여러 요청이 동시에 입장 가능한 경계를 넘을 때 중복 입장을 막을 수 없다. 입장 허용 인원과 상태 전환은 원자적으로 처리하고, 좌석 선점 단계에서도 최종 정합성을 확인해야 한다.

프로젝트에서 좌석 수 제한은 사용자가 한 번에 선택할 수 있는 수량을 1~6장 범위로 제한하는 방향으로 바뀌었다. 이런 제한은 프론트엔드 입력만 막아서는 안 되고, 서버 요청 검증에서도 같은 기준을 적용해야 한다. QR 티켓을 스캔해 사용 완료 상태로 바꾸는 경우에도 이미 사용된 티켓을 다시 사용할 수 없도록 상태 전환을 확인해야 한다.

### 테스트를 나눠서 보는 이유

- 대기열: 같은 사용자가 중복 등록되거나 대기 순서가 잘못 계산되지 않는가?
- 입장 처리: 여러 요청이 동시에 경계에 도달해도 허용 인원을 초과하지 않는가?
- 좌석 선점: 같은 좌석이 두 사용자에게 확정되지 않는가?
- 티켓 사용: 이미 USED인 티켓을 다시 사용 처리할 수 없는가?

각 기능을 하나의 성공 응답으로 묶어 판단하지 않고, 대기열·좌석·티켓 상태를 따로 확인해야 어떤 단계에서 정합성이 깨졌는지 찾기 쉽다.


## 결제 연동 오류는 함수 호출부와 모듈 연결부터 확인한다

Toss 결제 연동을 붙이는 과정에서는 프론트엔드에서 `payToss is not a function` 오류가 발생한 적이 있었다. 이 메시지는 결제 서버가 결제를 거절했다는 뜻이라기보다, 호출한 시점에 `payToss`가 실행 가능한 함수로 전달되지 않았다는 의미다.

이런 오류가 발생하면 결제 요청 파라미터부터 바꾸기보다 다음 순서로 확인해야 한다.

1. 실제로 import한 모듈에서 `payToss`를 export하고 있는가?
2. 호출하는 쪽의 import 방식과 export 방식이 맞는가? (named export와 default export 구분)
3. 해당 함수가 객체의 속성인지, 직접 호출할 함수인지 확인했는가?
4. 함수가 정의되기 전에 잘못된 객체나 응답 값을 호출하고 있지 않은가?
5. 브라우저 개발자 도구에서 실제 import 결과를 확인했는가?

이 오류의 핵심은 결제 API의 성공·실패와 JavaScript 함수 연결 문제를 구분하는 것이다. 호출 자체가 되지 않는 단계에서 서버 응답이나 결제 승인 로직을 먼저 의심하면 원인과 관계없는 부분을 수정할 수 있다.
