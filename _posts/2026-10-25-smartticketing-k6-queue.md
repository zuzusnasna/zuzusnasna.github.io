동시성 문제는 코드만 보고 해결됐다고 판단하기 어려워 실제로 여러 요청이 동시에 들어오는 상황을 만들어 검증했다.

## 테스트 목적

- 같은 좌석에 동시에 접근했을 때 중복 예매가 발생하지 않는가
- 대기열에서 같은 사용자가 중복 입장하지 않는가
- Redis 원자 연산이 경쟁 상황에서도 정확한가
- 응답 시간이 과도하게 증가하지 않는가

## k6

k6는 여러 가상 사용자가 동시에 HTTP 요청을 보내 부하 상황을 만들 수 있다.

```javascript
export const options = {
  vus: 5,
  duration: '1m'
};
```

단순히 성공 응답만 보는 것이 아니라 **DB 상태와 Redis 상태가 최종적으로 일치하는지**까지 확인해야 테스트 의미가 있다.

## 배운 점

성능 테스트는 숫자 하나를 얻는 작업이 아니라 **어떤 경쟁 상황을 만들고 무엇을 성공 조건으로 볼 것인지 정의하는 작업**이었다.

## 더 깊게 이해하기: 부하 테스트는 숫자보다 시나리오가 중요하다

대기열 테스트에서는 단순히 요청을 많이 보내는 것보다 실제 사용 흐름을 재현하는 것이 중요하다. 동시에 대기 번호를 조회하는 요청, 입장 가능한 사용자의 확인, 만료 또는 취소 흐름이 섞이면 시스템이 어떤 부하를 받는지 더 현실적으로 관찰할 수 있다.

k6의 체크는 개별 응답의 조건을 확인하고, 임계값(threshold)은 테스트 전체의 성능 기준을 표현한다. 응답 코드가 모두 200이어도 p95 지연 시간이 기준을 넘을 수 있으므로 성공률과 지연 지표를 함께 본다. 반대로 부하 생성기가 병목이 되면 서버 성능을 정확히 측정하지 못할 수 있다.

### 결과를 해석할 때
- VU 수, 실행 시간, 요청률 등 부하 조건을 기록한다.
- 평균뿐 아니라 p95·p99와 실패율을 확인한다.
- 대기열의 정합성은 응답 코드가 아니라 중복 번호·누락·입장 순서로 검증한다.
- 테스트 전후 DB와 Redis 상태를 확인해 데이터가 기대대로 남았는지 확인한다.

재현 가능한 테스트 조건이 있어야 이후 코드 변경의 결과를 공정하게 비교할 수 있다.
