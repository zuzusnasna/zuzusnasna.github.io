SmartTicketing의 대기열을 구현하면서 Redis Sorted Set을 사용했다.

대기열에서는 사용자의 현재 순번을 빠르게 조회할 수 있어야 했다.

## 1. 왜 Sorted Set인가

Redis Sorted Set은 각 member에 score를 함께 저장하고 score 순서로 데이터를 관리한다.

대기열에 들어온 순서를 score로 표현하면 사용자의 순위를 계산하기 편하다.

## 2. 순번 조회

특정 사용자의 앞에 몇 명이 있는지를 조회하면 현재 대기 순번을 계산할 수 있다.

```text
대기열

userA  score 100
userB  score 200
userC  score 300

userC의 앞에 있는 사용자 수 → 2명
현재 순번 → 3번
```

Redis의 Sorted Set을 이용하면 전체 대기열을 애플리케이션으로 가져와 직접 순위를 계산하지 않고 Redis에서 필요한 범위를 조회할 수 있다.

## 3. 배운 점

자료구조를 선택할 때 단순히 저장하기 편한지를 보는 것이 아니라 **서비스에서 가장 자주 필요한 조회가 무엇인지** 먼저 생각해야 한다.

대기열에서는 삽입 자체보다 현재 순번 조회가 중요한 요구사항이었고, 이 요구사항에 Sorted Set이 잘 맞았다.

## 더 깊게 이해하기: Sorted Set은 순위와 생명 주기를 함께 다뤄야 한다

Redis Sorted Set은 멤버와 점수를 연결하고 점수 순으로 관리한다. 대기열에서 점수를 진입 시각으로 사용하면 먼저 등록한 사용자가 앞에 위치하게 할 수 있다. 다만 같은 점수일 때의 순서, 멤버의 중복 등록, 취소나 만료 시 제거 시점을 명확히 해야 한다.

고정된 대기 번호를 사용자마다 저장하면 앞선 사용자가 빠질 때 이후 번호를 갱신해야 할 수 있다. 현재 순위를 조회하는 방식은 이런 재계산을 줄이지만, 조회 시점마다 순위가 달라질 수 있다는 점을 UI에서 설명해야 한다.

### 설계 검토
- 사용자 식별자가 ZSET 멤버로 중복되지 않도록 했는가?
- 취소·만료·입장 완료 시 점수 집합에서 제거하는가?
- Redis 데이터와 영속 DB의 상태가 달라질 때 복구 기준이 있는가?
- 점수 기준과 동점 처리 규칙을 테스트했는가?

자료구조는 빠른 조회를 제공하지만 업무 상태 전이와 장애 복구까지 대신하지는 않는다.
