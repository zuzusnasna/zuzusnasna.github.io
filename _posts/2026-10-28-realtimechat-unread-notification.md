채팅 서비스에서 메시지를 실시간으로 전달하는 것만으로는 부족했다. 사용자가 방을 보고 있지 않을 때 새 메시지가 왔다는 것을 알려줘야 했다.

## 미읽음 수

사용자별로 마지막으로 읽은 메시지 위치를 기준으로 이후 메시지 수를 계산한다.

```text
마지막 읽은 위치 = 100
현재 방의 마지막 메시지 = 103
→ 미읽음 3개
```

사용자가 해당 방에 들어가 읽음 처리를 하면 숫자를 줄인다.

## 실시간 알림

현재 보고 있는 채팅방과 다른 방에서 메시지가 발생하면 방 목록의 미읽음 숫자를 갱신하도록 했다.

```text
새 메시지
 ↓
WebSocket event
 ↓
현재 보고 있는 room인가?
 ├─ Yes → 채팅 화면 갱신
 └─ No  → 방 목록 unread 증가
```

## 실제 디버깅에서 배운 점

API에서는 `unreadCount`가 정상적으로 내려오는데 화면에 숫자가 보이지 않는 경우도 있었다. 이런 문제에서는 DB → API → React state → 렌더링 중 어느 단계에서 값이 사라지는지 각각 확인해야 한다.

## 배운 점

실시간 기능은 서버 이벤트만 구현한다고 끝나는 것이 아니라 **서버 데이터와 화면 상태를 연결하는 전체 흐름을 검증해야 한다**는 것을 배웠다.

## 더 깊게 이해하기: 읽음 수는 사용자별 읽음 위치를 모델링하는 문제다

메시지마다 사용자별 읽음 여부를 저장하면 상세한 읽음 정보를 얻을 수 있지만, 사용자·방·메시지 수가 커질수록 기록이 늘어난다. 사용자별 마지막으로 읽은 메시지 ID나 읽은 시각을 저장하면 그 위치 이후의 메시지를 기준으로 읽지 않은 수를 계산할 수 있다. 어느 방식이 맞는지는 개인별 읽음 표시가 필요한지와 조회 패턴에 따라 달라진다.

숫자가 화면에 나타나지 않을 때는 UI만 보지 말고 API 응답, 읽음 위치 갱신, 방 진입 이벤트, 프론트엔드 상태 반영을 분리해서 확인해야 한다.

### 검증 시나리오
- 방에 진입하면 읽음 위치가 갱신되고 숫자가 줄어드는가?
- 다른 방에서 새 메시지를 받으면 해당 방의 숫자만 증가하는가?
- 메시지가 없는 신규 방과 읽음 위치가 없는 상태를 구분하는가?
- 새로고침 후에도 서버의 읽음 상태와 화면이 일치하는가?

읽음 기능은 뱃지 표시가 아니라 메시지 시점과 사용자별 읽음 위치 사이의 관계를 일관되게 관리하는 기능이다.
