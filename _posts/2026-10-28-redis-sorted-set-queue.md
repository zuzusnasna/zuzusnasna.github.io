대기열의 핵심 요구사항은 순서를 저장하는 것보다 **현재 사용자가 몇 번째인지 빠르게 조회하는 것**이었다.

## Sorted Set

Redis Sorted Set은 member와 score를 함께 저장하고 score 순으로 정렬한다.

```text
userA → 100
userB → 101
userC → 102
```

특정 사용자의 score보다 작은 데이터를 세면 앞에 있는 사용자 수를 계산할 수 있다.

```text
내 앞의 사용자 수 + 1 = 현재 순번
```

Redis의 `ZCOUNT` 등을 이용하면 이 값을 빠르게 조회할 수 있다.

## 왜 DB만 사용하지 않았나

대기순번은 사용자가 반복적으로 조회할 수 있는 값이다. 매번 큰 테이블을 정렬해 계산하면 DB 부하가 커질 수 있어 Redis를 빠른 순번 조회에 사용하고 DB를 원본 데이터로 두는 구조를 선택했다.

## 배운 점

Redis는 무조건 캐시로 사용하는 것이 아니라 **조회 요구사항에 맞는 자료구조를 선택하는 것**이 핵심이었다.

## 더 깊게 이해하기: 순위와 상태 전이는 따로 검증한다

Sorted Set은 점수 순으로 멤버를 조회할 수 있어 대기열 순위를 계산하는 데 유용하다. 하지만 순위 자료구조 자체가 사용자의 업무 상태를 모두 표현하는 것은 아니다. 등록, 대기, 입장 가능, 입장 완료, 취소, 만료처럼 상태 전이를 별도로 정의하고, 각 상태에서 허용되는 작업을 제한해야 한다.

예를 들어 사용자가 입장 가능 상태가 된 뒤 브라우저를 여러 번 새로고침하거나 동시에 여러 요청을 보내더라도 입장 처리가 중복되어서는 안 된다. Redis의 점수 집합에서 멤버를 제거하는 것과 DB에서 입장 상태를 변경하는 작업이 서로 다른 저장소에 걸쳐 있다면, 한쪽만 성공했을 때의 복구 정책도 필요하다.

### 검증할 시나리오
- 같은 사용자의 등록 요청을 반복해도 한 항목만 존재하는가?
- 입장 가능 상태에서 중복 입장 요청을 보내도 결과가 한 번만 반영되는가?
- 만료된 사용자가 순위에 남거나 다시 입장할 수 있지 않은가?
- Redis와 DB 상태가 어긋났을 때 재처리로 복구할 수 있는가?

대기열은 빠른 순위 조회와 안전한 상태 전이를 함께 설계해야 완성된다.
