새 팀 프로젝트 아이디어를 정리하면서 단순 CRUD 서비스보다 **개발자가 DB나 코드를 변경했을 때 성능이 나빠졌는지 자동으로 확인하는 시스템**을 설계했다.

## 문제

개발 환경에서는 데이터가 적어서 쿼리가 빠르지만 실제 운영 규모의 데이터에서는 갑자기 느려질 수 있다.

```text
코드 변경
   ↓
SQL 변경
   ↓
대량 데이터에서 성능 저하
   ↓
운영에서 발견
```

목표는 배포 전에 성능 회귀를 발견하는 것이다.

## 기본 구조

```text
React
 ↓
Spring Boot API
 ↓
Test Runner
 ↓
MySQL 테스트 DB
 ↓
실행 시간 / EXPLAIN 수집
 ↓
이전 결과와 비교
```

## 핵심 기능

- 테스트용 대량 데이터 생성
- 기준 쿼리 등록
- 변경 후 쿼리 실행
- 실행 시간 측정
- 실행 계획 비교
- 이전 결과 대비 성능 회귀 판정
- 결과 이력 관리

## 설계할 때 생각한 것

성능이 10% 느려졌다고 무조건 실패로 볼 수는 없다. 실행 환경의 편차가 있기 때문에 여러 번 실행하고 기준값과 비교하는 과정이 필요하다.

## 배운 점

성능 개선을 사람이 직접 하는 것뿐 아니라 **성능 저하를 자동으로 발견할 수 있게 만드는 것**도 백엔드 시스템의 중요한 역할이 될 수 있다고 생각했다.

## 설계 판단을 더 구체화하기: 무엇을 성능 회귀라고 볼 것인가

성능 회귀를 자동으로 판정하려면 먼저 비교 조건을 통제해야 한다. 같은 SQL이라도 데이터 건수, 인덱스, 캐시 상태, 동시 실행 부하, DB 설정이 다르면 실행 시간이 달라진다. 따라서 측정 결과를 단일 숫자로 저장하기보다 실행 환경과 데이터셋 버전, SQL 버전, 실행 계획을 함께 기록해야 비교 결과를 해석할 수 있다.

실행 시간이 10% 증가했다는 이유만으로 항상 실패로 판정하는 것도 위험하다. 측정 노이즈가 기준을 넘었는지, 실행 계획이 바뀌었는지, 실제 처리 행 수가 달라졌는지를 함께 살펴야 한다. 반복 실행과 중앙값·백분위수 같은 통계를 사용하면 단일 측정값에 덜 민감해질 수 있다.

### 첫 버전의 범위
- 기준 SQL과 테스트 데이터셋을 버전으로 관리한다.
- EXPLAIN 결과와 실행 시간을 함께 저장한다.
- 테스트 환경의 차이를 결과에 표시한다.
- 자동 실패 판정과 사람이 검토해야 하는 경고를 구분한다.

이 서비스의 어려운 부분은 SQL을 실행하는 기능 자체보다, 결과를 공정하게 비교하고 왜 느려졌는지 설명 가능한 근거를 제공하는 데 있다.
