RealTimeChat을 EC2에 배포한 뒤 빠르게 여러 메시지를 전송했을 때 로컬 환경에서는 느끼지 못했던 지연이 발생했다.

처음에는 WebSocket이나 메시지 저장 순서를 의심했지만, 서버 자원 상태부터 확인하기로 했다.

## 1. 문제 상황

EC2 환경에서 메시지를 연속으로 전송하면 약 1초 정도의 지연이 느껴졌다. 동시에 데이터베이스에 저장되는 메시지 순서도 확인할 필요가 있었다.

하지만 원인을 한 번에 여러 곳에서 찾기보다 **서버 자원 부족 여부를 먼저 확인**했다.

## 2. 서버 자원 확인

Free Tier 수준의 EC2 인스턴스에서 Docker로 여러 서비스를 실행하고 있었다.

확인 과정에서 메모리와 Swap 사용량이 높았고, 이후에는 I/O wait도 상당히 높게 나타났다.

```text
RAM 약 770MiB 사용
Swap 약 1.0GiB 사용
Load average 1.81 / 3.06 / 3.05
```

이후 다른 시점에서는 Swap 사용량이 약 1.4GiB까지 증가했고 I/O wait가 약 84~86% 수준으로 관찰됐다.

## 3. 원인 범위 좁히기

당시에는 애플리케이션 두 개뿐 아니라 모니터링을 위한 Prometheus와 Grafana도 함께 실행하고 있었다.

그래서 애플리케이션 코드만 수정하기보다 **실제로 필요한 서비스와 부가적인 서비스의 자원 사용량을 분리해서 확인**했다.

모니터링 프로필을 중지한 뒤 메모리 사용량은 약 706MiB, Swap 사용량은 약 999MiB 수준으로 내려갔다.

이를 통해 작은 EC2 인스턴스에서 여러 컨테이너를 동시에 운영하는 것 자체가 지연에 영향을 줄 수 있다는 것을 확인했다.

## 4. 먼저 자원 문제를 해결한 이유

메시지 순서 문제와 WebSocket 처리 문제를 바로 수정할 수도 있었지만, 서버가 Swap을 많이 사용하고 I/O wait가 높은 상태에서는 애플리케이션 로직을 변경해도 정확한 성능을 판단하기 어렵다.

따라서 이번 분석에서는 다음 순서로 접근했다.

1. EC2 CPU / 메모리 / Swap 확인
2. Docker 컨테이너별 자원 사용량 확인
3. 모니터링 컨테이너 중지
4. 서버 상태 변화 확인
5. 이후 메시지 지연과 저장 순서 재검증

## 5. 배운 점

성능 문제를 만났을 때 애플리케이션 코드부터 수정할 필요는 없다.

특히 실제 서버에서는 **CPU, 메모리, Swap, 디스크 I/O 같은 시스템 상태가 애플리케이션 성능에 직접 영향을 줄 수 있다.**

이번 문제를 통해 기능의 정상 동작과 성능 문제를 분리해서 보고, 먼저 관측 가능한 데이터로 원인 범위를 좁혀야 한다는 점을 배웠다.

앞으로는 메시지 순서 문제도 별도로 검증하면서 WebSocket → Redis → DB로 이어지는 전체 흐름을 단계별로 확인할 예정이다.

## 분석을 재현 가능한 운영 기록으로 만들기

자원 문제를 조사할 때는 측정 시각과 실행 중인 컨테이너 구성을 함께 기록해야 한다. 메모리와 Swap 사용량이 높다는 사실은 중요한 단서지만, 그것만으로 지연의 유일한 원인이라고 확정할 수는 없다. 컨테이너별 메모리, CPU, 디스크 I/O, 네트워크, 애플리케이션 지표를 같은 시간대에 비교해야 한다.

특히 I/O wait가 높다면 CPU 연산이 부족한 상황과 다르게 디스크 작업이 완료되기를 기다리는 시간이 길 수 있다. Swap 사용이 늘어난 환경에서는 페이지 회수와 디스크 접근이 추가 지연을 만들 수 있다. 다만 원인을 확정하려면 디스크 지표와 프로세스 상태를 함께 관찰해야 한다.

### 다음 검증 단계
1. 모니터링 컨테이너를 켠 상태와 끈 상태의 지표를 같은 부하로 비교한다.
2. 앱 인스턴스 수와 메모리 제한을 바꾸되 한 번에 한 조건만 변경한다.
3. 메시지 지연과 DB 저장 시각을 함께 기록한다.
4. 자원 압박이 줄어든 뒤에도 남는 순서 문제를 별도 재현한다.

관측 결과와 추측을 분리해 기록해야 다음 수정이 실제 원인을 해결했는지 판단할 수 있다.


## 구현 중 발생한 문제를 분리해서 확인하기

실시간 채팅은 메시지 전송 외에도 로그인, 방 접근 권한, 메시지 저장, 여러 서버 사이의 전달, 읽음 상태가 서로 연결되어 있었다. 그래서 한 단계의 값이 정상이라고 전체 기능이 정상이라고 판단하지 않았다.

### 1. 인증과 WebSocket 권한

REST API에서 로그인 여부를 확인하는 것과 STOMP 메시지를 허용하는 것은 별도로 확인해야 한다. 사용자가 로그인했더라도 요청에 포함된 room ID가 실제 참여 중인 방인지 서버에서 검증해야 한다.

~~~text
HTTP 로그인 상태 확인
        ↓
WebSocket / STOMP 연결
        ↓
SEND / SUBSCRIBE 권한 확인
        ↓
해당 방 참여 여부 확인
        ↓
메시지 처리
~~~

프론트엔드에서 버튼이나 방 목록을 숨기는 것은 UX 처리일 뿐 보안 경계가 아니다. 서버가 최종 권한을 확인해야 한다.

### 2. 로컬과 EC2 환경 차이

로컬에서는 메시지가 빠르게 도착하더라도 EC2에서는 인스턴스 자원, Docker 구성, DB I/O가 달라 결과가 달라질 수 있었다. 환경 변수는 .env로 분리하고, 로컬 개발용 포트와 컨테이너 내부 포트를 구분해 확인했다.

문제가 생겼을 때는 먼저 실제 컨테이너와 포트가 어떻게 떠 있는지 확인하고, 그다음 애플리케이션 로그와 DB 상태를 확인하는 순서로 원인을 좁혔다. 환경 설정을 여러 개 한꺼번에 바꾸면 어느 변경이 효과가 있었는지 알기 어려워 한 번에 하나씩 검증하는 것이 중요했다.

### 3. 메시지 순서와 성능은 분리해서 보기

EC2에서 연속 메시지 전송이 약 1초 지연됐을 때, 먼저 확인한 것은 WebSocket 코드가 아니라 메모리·Swap·I/O wait였다. 모니터링 컨테이너를 중지한 뒤 자원 사용량이 내려간 것을 확인했고, 자원 압박을 줄인 다음 메시지 순서 문제를 별도로 검증하기로 했다.

이 접근은 순서 문제가 해결됐다는 의미가 아니라, 성능 저하가 있는 환경에서 순서 로직까지 동시에 바꾸지 않고 원인을 분리했다는 의미다. 부하 테스트 결과도 HTTP 성공률만으로 판단하지 않고 WebSocket 수신 수, cross-instance 전달 지연, 저장된 메시지 순서를 함께 확인해야 한다.
