RealTimeChat을 EC2에 배포한 뒤 빠르게 여러 메시지를 전송했을 때 로컬 환경에서는 느끼지 못했던 지연이 발생했다.

처음에는 WebSocket이나 메시지 저장 순서를 의심했지만, 서버 자원 상태부터 확인하기로 했다.

## 1. 문제 상황

EC2 환경에서 메시지를 연속으로 전송하면 약 1초 정도의 지연이 느껴졌다. 동시에 데이터베이스에 저장되는 메시지 순서도 확인할 필요가 있었다.

하지만 원인을 한 번에 여러 곳에서 찾기보다 **서버 자원 부족 여부를 먼저 확인**했다.

## 2. 서버 자원 확인

Free Tier 수준의 EC2 인스턴스에서 Docker로 여러 서비스를 실행하고 있었다.

확인 과정에서 메모리와 Swap 사용량이 높았고, 이후에는 I/O wait도 상당히 높게 나타났다.

```text
RAM 약 770MiB 사용
Swap 약 1.0GiB 사용
Load average 1.81 / 3.06 / 3.05
```

이후 다른 시점에서는 Swap 사용량이 약 1.4GiB까지 증가했고 I/O wait가 약 84~86% 수준으로 관찰됐다.

## 3. 원인 범위 좁히기

당시에는 애플리케이션 두 개뿐 아니라 모니터링을 위한 Prometheus와 Grafana도 함께 실행하고 있었다.

그래서 애플리케이션 코드만 수정하기보다 **실제로 필요한 서비스와 부가적인 서비스의 자원 사용량을 분리해서 확인**했다.

모니터링 프로필을 중지한 뒤 메모리 사용량은 약 706MiB, Swap 사용량은 약 999MiB 수준으로 내려갔다.

이를 통해 작은 EC2 인스턴스에서 여러 컨테이너를 동시에 운영하는 것 자체가 지연에 영향을 줄 수 있다는 것을 확인했다.

## 4. 먼저 자원 문제를 해결한 이유

메시지 순서 문제와 WebSocket 처리 문제를 바로 수정할 수도 있었지만, 서버가 Swap을 많이 사용하고 I/O wait가 높은 상태에서는 애플리케이션 로직을 변경해도 정확한 성능을 판단하기 어렵다.

따라서 이번 분석에서는 다음 순서로 접근했다.

1. EC2 CPU / 메모리 / Swap 확인
2. Docker 컨테이너별 자원 사용량 확인
3. 모니터링 컨테이너 중지
4. 서버 상태 변화 확인
5. 이후 메시지 지연과 저장 순서 재검증

## 5. 배운 점

성능 문제를 만났을 때 애플리케이션 코드부터 수정할 필요는 없다.

특히 실제 서버에서는 **CPU, 메모리, Swap, 디스크 I/O 같은 시스템 상태가 애플리케이션 성능에 직접 영향을 줄 수 있다.**

이번 문제를 통해 기능의 정상 동작과 성능 문제를 분리해서 보고, 먼저 관측 가능한 데이터로 원인 범위를 좁혀야 한다는 점을 배웠다.

앞으로는 메시지 순서 문제도 별도로 검증하면서 WebSocket → Redis → DB로 이어지는 전체 흐름을 단계별로 확인할 예정이다.
