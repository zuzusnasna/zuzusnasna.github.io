프로젝트를 EC2에 배포하면서 Docker를 단순히 실행 명령어로만 보지 않고 **애플리케이션 실행 환경을 패키징하는 방법**으로 이해하게 됐다.

## Image와 Container

```text
Dockerfile
   ↓ build
Image
   ↓ run
Container
```

Image는 실행에 필요한 파일과 환경을 포함하고 Container는 그 이미지를 실행한 인스턴스다.

## Compose

여러 서비스를 함께 실행해야 하는 경우 Docker Compose로 관리할 수 있다.

```text
nginx
 ├─ app-1
 ├─ app-2
 ├─ mysql
 └─ redis
```

## 환경 변수

DB 주소나 비밀번호 같은 환경별 설정을 이미지에 하드코딩하지 않고 `.env`나 배포 환경 변수로 분리했다.

## 배운 점

Docker의 장점은 단순히 서버에서 실행하기 편하다는 것보다 **개발/배포 환경의 차이를 줄이고 여러 서비스를 동일한 방식으로 관리할 수 있다는 점**이었다.

## 더 깊게 이해하기: 컨테이너는 가상 머신과 다르다

컨테이너는 별도의 운영체제 커널을 포함한 가상 머신이 아니라 호스트 커널을 공유하면서 프로세스와 자원 사용을 격리하는 방식이다. 이미지에는 실행에 필요한 파일과 기본 설정이 포함되고, 컨테이너는 그 이미지로부터 생성된 실행 인스턴스다. 따라서 컨테이너를 삭제해도 외부 볼륨에 저장한 데이터는 남을 수 있고, 컨테이너 내부에만 저장한 데이터는 삭제 시 사라질 수 있다.

운영 환경에서는 이미지 버전, 환경변수, 포트 매핑, 네트워크, 볼륨, 재시작 정책을 각각 구분해야 한다. 컨테이너가 실행 중이라는 사실만으로 애플리케이션이 정상 상태라는 뜻은 아니다.

### 실습 점검
- 설정값을 이미지에 굽지 않고 실행 시 주입하는가?
- DB 데이터처럼 유지되어야 하는 파일은 볼륨에 저장하는가?
- 컨테이너 로그와 애플리케이션 로그를 구분해 확인할 수 있는가?
- 서비스 간 통신에 호스트 포트와 컨테이너 내부 포트를 혼동하지 않는가?

컨테이너 운영의 핵심은 실행 명령보다 환경을 재현하고 상태를 관측하며 데이터를 안전하게 유지하는 데 있다.
