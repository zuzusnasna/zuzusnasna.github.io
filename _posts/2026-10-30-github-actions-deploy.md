프로젝트를 수정할 때마다 서버에 직접 접속해 빌드하고 실행하는 방식은 반복 작업이 많고 실수하기 쉽다. 그래서 GitHub Actions를 이용해 변경 사항을 배포 과정과 연결했다.

## 기본 흐름

```text
git push / merge
      ↓
GitHub Actions
      ↓
Build / Test
      ↓
Docker Image
      ↓
EC2 Deploy
      ↓
Container Restart
```

## CI와 CD

CI는 코드가 변경될 때 빌드와 테스트를 자동으로 검증하는 과정이고 CD는 검증된 결과를 실제 환경에 전달하는 과정이다.

## 실패했을 때

Action이 성공했다고 애플리케이션이 반드시 정상 동작하는 것은 아니다. 빌드 성공과 실제 서버 실행 성공은 별개의 단계다.

```text
Build 성공
 ≠
배포 성공
 ≠
서비스 정상
```

## 배운 점

자동 배포의 핵심은 명령어 하나를 자동으로 실행하는 것이 아니라 **코드 변경 → 검증 → 배포 → 실행 확인이라는 흐름을 반복 가능하게 만드는 것**이다.

## 더 깊게 이해하기: CI와 CD는 자동 실행보다 신뢰 가능한 절차가 핵심이다

CI는 코드 변경을 빌드와 테스트로 빠르게 검증하는 과정이고, CD는 검증된 산출물을 환경에 전달하는 과정이다. 워크플로가 초록색으로 끝났다고 실제 서비스까지 정상이라는 뜻은 아니다. 빌드 성공, 배포 성공, 애플리케이션 기동, 헬스 체크, 핵심 사용자 흐름은 서로 다른 검증 단계다.

배포 자동화는 실패 시 어디까지 변경되었는지 파악할 수 있어야 한다. 비밀값은 GitHub Secrets 같은 안전한 저장소로 전달하고 로그에 출력하지 않는다. 운영 서버에서 수동으로 변경한 설정은 다음 자동 배포에서 사라질 수 있으므로 코드와 서버 설정의 책임을 명확히 해야 한다.

### 배포 파이프라인 체크리스트
- 빌드·테스트와 배포 단계를 분리했는가?
- 배포 대상 브랜치와 권한이 명확한가?
- 실패한 단계와 로그를 확인할 수 있는가?
- 배포 후 헬스 체크와 롤백 방법이 준비되어 있는가?

자동화의 목적은 버튼을 줄이는 것이 아니라 같은 절차를 반복 가능하게 만들고 실수를 줄이는 것이다.
