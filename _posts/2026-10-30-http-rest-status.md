REST API를 만들면서 HTTP 상태 코드를 단순한 숫자로 외우지 않고 **요청의 결과를 클라이언트에게 설명하는 정보**로 이해하려고 정리했다.

## 자주 사용하는 상태 코드

| 코드 | 의미 | 예시 |
|---|---|---|
| 200 | 성공 | 조회 성공 |
| 201 | 생성 | 회원 생성 |
| 204 | 성공했지만 응답 본문 없음 | 삭제 성공 |
| 400 | 잘못된 요청 | 필수값 누락 |
| 401 | 인증 필요 | 로그인하지 않음 |
| 403 | 권한 없음 | 다른 사용자의 리소스 접근 |
| 404 | 대상 없음 | 존재하지 않는 방 |
| 409 | 상태 충돌 | 이미 예약된 좌석 |

## REST 설계에서 중요한 점

URL에는 동작보다 리소스를 표현하고 HTTP Method로 의도를 구분하는 방식이 일반적이다.

```text
GET    /rooms
POST   /rooms
GET    /rooms/{id}
PATCH  /rooms/{id}
DELETE /rooms/{id}
```

## 배운 점

좋은 API는 Controller 코드만 깔끔한 것이 아니라 **요청과 응답의 의미가 일관되고 클라이언트가 결과를 예측할 수 있어야 한다**고 정리했다.

## 더 깊게 이해하기: 상태 코드는 API의 일부 계약이다

HTTP 상태 코드는 클라이언트가 요청 결과를 일관되게 해석하도록 돕는다. 200은 성공한 조회나 처리, 201은 리소스 생성, 204는 응답 본문 없이 성공한 경우에 적합할 수 있다. 400은 잘못된 요청, 401은 인증이 필요한 상태, 403은 인증은 되었지만 권한이 없는 상태, 404는 대상이 없거나 노출하지 않을 때, 409는 현재 상태와 충돌하는 요청을 표현할 수 있다.

상태 코드와 응답 본문은 함께 설계해야 한다. 모든 실패를 200으로 반환하고 본문에 오류를 넣으면 HTTP 클라이언트, 모니터링, 재시도 정책이 실패를 올바르게 감지하기 어렵다. 반대로 내부 예외 메시지를 그대로 반환하면 구현 세부 정보가 외부로 노출될 수 있다.

### API 계약 검토
- 생성과 수정, 삭제의 성공 결과가 명확한가?
- 인증 실패와 권한 부족을 구분하는가?
- 오류 응답에 코드와 사용자에게 안전한 메시지가 있는가?
- 클라이언트가 상태 코드만으로 재시도 여부를 판단할 수 있는가?

REST API는 URL만 잘 만드는 것이 아니라 메서드, 상태 코드, 요청·응답 구조가 함께 일관된 계약을 이루는 것이다.
