예외 처리는 단순히 오류 메시지를 출력하는 기능이 아니라 **실패했을 때 프로그램이 어떤 상태로 동작해야 하는지를 결정하는 설계**다.

## 기본 구조

```java
try {
    service.execute();
} catch (IllegalArgumentException e) {
    // 잘못된 입력 처리
} finally {
    // 정리 작업
}
```

## Checked와 Unchecked

Checked Exception은 컴파일 단계에서 처리를 요구한다. 대표적으로 파일이나 네트워크처럼 외부 자원과 관련된 작업에서 볼 수 있다.

Unchecked Exception은 `RuntimeException` 계열이며 잘못된 상태나 입력 등을 표현하는 데 많이 사용한다.

## 실무에서 중요한 것

모든 예외를 `catch (Exception e)`로 잡고 무조건 로그만 남기면 원인을 숨길 수 있다. 서비스 계층에서는 의미 있는 예외로 변환하고 Controller에서는 사용자에게 적절한 HTTP 응답을 내려주는 식으로 책임을 나누는 것이 중요하다.

## 배운 점

예외 처리는 많이 잡는 것이 목적이 아니라 **어디에서 복구할 수 있는지와 어디에서 실패를 전달해야 하는지를 구분하는 것**이다.

## 더 깊게 이해하기: 예외는 계층 간 실패 정보를 전달한다

예외를 어느 계층에서 처리할지는 해당 계층이 실패를 복구할 수 있는지에 따라 결정한다. 저장소 계층에서 발생한 예외를 서비스가 업무 의미에 맞는 예외로 변환할 수 있고, 컨트롤러 앞의 공통 처리 계층은 이를 일관된 HTTP 응답으로 바꿀 수 있다. 모든 계층에서 예외를 잡고 로그를 남기면 같은 오류가 중복 기록되고 원래 스택이 흐려질 수 있다.

사용자 입력 오류, 권한 오류, 외부 시스템 장애, 예상하지 못한 프로그램 오류는 대응 방법이 다르다. 사용자에게는 안전하고 이해 가능한 메시지를 제공하되, 내부 로그에는 원인 추적에 필요한 정보를 남기고 비밀값은 제외해야 한다.

### 오류 처리 점검
- 복구할 수 있는 예외만 처리하고 나머지는 적절히 전파하는가?
- 예외를 성공 응답으로 바꾸거나 조용히 무시하지 않는가?
- API 오류 형식과 상태 코드가 일관적인가?
- 같은 예외가 여러 계층에서 중복 로깅되지 않는가?

예외 처리는 오류를 없애는 것이 아니라 실패가 발생해도 시스템 상태와 사용자 응답을 예측 가능하게 만드는 설계다.
