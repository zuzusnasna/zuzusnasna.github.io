Java는 소스 코드를 한 번 기계어로 변환하고 끝나는 방식이 아니다. 먼저 Java 컴파일러가 소스 코드를 바이트코드로 변환하고, JVM은 이 바이트코드를 실행하면서 자주 실행되는 코드를 기계어로 컴파일해 성능을 높일 수 있다.

이때 실행 중인 프로그램의 정보를 바탕으로 코드를 최적화하는 컴파일러가 **JIT(Just-In-Time) Compiler**다. JIT를 이해하려면 먼저 Java 코드가 실제로 실행되는 흐름부터 살펴봐야 한다.

## 1. Java 소스 코드는 어떻게 실행될까?

Java 프로그램의 실행은 크게 다음 순서로 진행된다.

```text
Hello.java
   |
   | javac (Java Compiler)
   v
Hello.class (Bytecode)
   |
   | JVM
   v
Interpreter로 바이트코드 실행
   |
   | 자주 실행되는 코드 감지
   v
JIT Compiler가 기계어로 컴파일
   |
   v
컴파일된 기계어 실행
```

먼저 개발자가 작성한 `.java` 파일을 `javac`가 컴파일하면 `.class` 파일이 만들어진다. 이 파일에는 CPU가 직접 실행하는 기계어가 아니라 JVM이 이해하는 **바이트코드(Bytecode)**가 들어 있다.

예를 들어 다음 코드를 작성했다고 하자.

```java
public class Calculator {
    public static int add(int a, int b) {
        return a + b;
    }

    public static void main(String[] args) {
        System.out.println(add(10, 20));
    }
}
```

컴파일은 다음 명령으로 수행할 수 있다.

```bash
javac Calculator.java
```

컴파일 결과로 `Calculator.class`가 생성된다. 바이트코드는 다음 명령으로 확인할 수 있다.

```bash
javap -c Calculator
```

출력되는 명령어는 `iload`, `iadd`, `ireturn`처럼 JVM 명령어로 구성된다. 즉, Java 컴파일러가 만드는 결과물은 운영체제나 CPU에 종속된 실행 파일이 아니라 JVM이 실행할 수 있는 바이트코드다.

## 2. 인터프리터(Interpreter)는 어떤 역할을 할까?

JVM은 바이트코드를 실행하는 방법 중 하나로 인터프리터를 사용한다.

인터프리터는 바이트코드 명령을 읽고 해석한 뒤 실행한다. 프로그램을 시작할 때 모든 코드를 기계어로 컴파일할 필요가 없기 때문에 초기 실행을 빠르게 시작할 수 있다는 장점이 있다.

하지만 같은 코드가 반복해서 실행될 때마다 바이트코드를 해석하는 작업이 계속 발생할 수 있다. 반복 실행이 많은 프로그램에서는 이 과정이 성능 부담이 될 수 있다.

예를 들어 다음 메서드를 생각해 보자.

```java
public static int calculate(int value) {
    return value * 2 + 10;
}

public static void main(String[] args) {
    long total = 0;

    for (int i = 0; i < 10_000_000; i++) {
        total += calculate(i);
    }

    System.out.println(total);
}
```

`calculate()`는 반복문 안에서 매우 많이 호출된다. 이런 메서드는 실행 중 자주 호출되는 코드로 관찰될 수 있다. JVM은 실행 횟수 등의 정보를 수집하고, 성능상 이점이 있다고 판단되는 코드를 JIT 컴파일 대상으로 삼는다.

## 3. JIT Compiler란?

JIT는 Just-In-Time의 약자로, 프로그램이 실행되는 도중 필요한 코드를 기계어로 컴파일하는 방식이다.

인터프리터가 바이트코드를 해석해 실행하는 동안 JVM은 메서드 호출 횟수나 반복문 실행 횟수 같은 실행 정보를 수집한다. 자주 실행되는 코드 영역을 발견하면 JIT 컴파일러가 해당 코드를 현재 실행 환경에 맞는 기계어로 변환할 수 있다.

```text
바이트코드
   |
   v
인터프리터 실행 + 실행 정보 수집
   |
   v
자주 실행되는 메서드 / 반복문 감지
   |
   v
JIT 컴파일
   |
   v
기계어를 Code Cache에 저장
   |
   v
이후 실행에서 컴파일된 코드 활용
```

여기서 중요한 점은 **모든 바이트코드를 처음부터 전부 기계어로 바꾸는 것이 아니라는 것**이다. 실행 중 실제로 자주 사용되는 부분을 찾아 컴파일하기 때문에 불필요한 컴파일 비용을 줄일 수 있다.

## 4. Hot Code와 HotSpot

JVM에서 실행 빈도가 높아 최적화 대상으로 주목하는 코드를 흔히 Hot Code라고 부른다. 메서드가 반복 호출되거나 반복문이 많이 실행되는 경우가 대표적이다.

HotSpot JVM은 실행 중 수집한 프로파일 정보를 활용해 어떤 코드가 자주 실행되는지 판단한다. 이처럼 실행 정보를 기반으로 최적화를 수행하는 것이 JIT의 핵심이다.

예를 들어 쇼핑몰 서버에서 다음 기능이 있다고 가정해 보자.

- 상품 가격과 할인율을 계산하는 메서드
- 주문 가능 수량을 확인하는 메서드
- 관리자만 사용하는 월간 통계 메서드

모든 기능이 같은 빈도로 호출되지는 않는다. 상품 가격 계산은 요청마다 실행될 수 있지만 월간 통계 기능은 하루에 몇 번만 실행될 수 있다. JIT는 실제 실행 빈도와 프로파일을 바탕으로 자주 실행되는 코드를 우선 최적화할 수 있다.

## 5. JIT는 어떤 방식으로 코드를 최적화할까?

JIT는 단순히 바이트코드를 기계어로 바꾸는 것에서 끝나지 않는다. 실행 중 수집한 정보를 바탕으로 불필요한 작업을 줄이는 최적화도 수행할 수 있다.

### 5-1. 메서드 인라이닝(Method Inlining)

메서드를 호출하는 대신 메서드의 실행 내용을 호출한 위치에 삽입하는 최적화다.

```java
public int discount(int price) {
    return price * 9 / 10;
}

public int finalPrice(int price) {
    return discount(price);
}
```

일반적인 메서드 호출에는 호출과 복귀에 따른 비용이 발생한다. 메서드가 작고 호출 빈도가 높다면 JIT는 상황에 따라 메서드 내용을 호출 위치에 포함하는 인라이닝을 수행할 수 있다.

개념적으로는 다음과 같이 이해할 수 있다.

```java
// 원래 코드
int result = discount(price);

// 인라이닝을 단순화해 표현한 모습
int result = price * 9 / 10;
```

실제 컴파일러가 수행하는 최적화는 메서드 크기, 호출 관계, 실행 프로파일 등 여러 조건에 따라 달라진다.

### 5-2. 루프 최적화(Loop Optimization)

반복문은 실행 횟수가 많기 때문에 최적화 효과가 클 수 있다. JIT는 반복문 내부의 불필요한 연산을 줄이거나 반복 실행에 적합한 기계어를 생성하는 등의 최적화를 수행할 수 있다.

다만 모든 반복문이 같은 방식으로 최적화되는 것은 아니다. 반복 횟수와 데이터 접근 형태, 코드 구조에 따라 결과가 달라진다.

### 5-3. 이스케이프 분석(Escape Analysis)

객체가 생성된 메서드 또는 스레드 범위를 벗어나 외부에서 사용되는지 분석하는 기법이다.

```java
class Point {
    int x;
    int y;

    Point(int x, int y) {
        this.x = x;
        this.y = y;
    }
}

public int sum() {
    Point point = new Point(10, 20);
    return point.x + point.y;
}
```

이 코드에서 `Point` 객체가 메서드 밖으로 전달되거나 외부에 저장되지 않는다는 사실을 JIT가 증명할 수 있다면, 객체 할당을 제거하거나 필요한 값을 레지스터 등에 배치하는 최적화를 고려할 수 있다.

이와 관련해 자주 언급되는 개념이 **스칼라 치환(Scalar Replacement)**이다. 객체 전체를 실제로 생성하는 대신 객체의 필드를 개별 값으로 다루는 방식이다.

주의할 점은 이스케이프 분석이 곧바로 모든 객체를 스택에 할당한다는 뜻은 아니라는 것이다. 실제 최적화 여부는 JVM 구현과 코드 상황에 따라 달라진다.

## 6. C1과 C2 컴파일러, Tiered Compilation

HotSpot JVM은 대표적으로 C1과 C2 컴파일러를 사용한다.

| 구분 | C1 Compiler | C2 Compiler |
| --- | --- | --- |
| 특징 | 비교적 빠른 컴파일 | 더 많은 분석을 통한 고도화된 최적화 |
| 목적 | 빠르게 컴파일된 코드 제공 | 장시간 실행되는 Hot Code의 성능 최적화 |
| 관점 | 컴파일 비용을 줄이는 데 유리 | 최적화에 더 많은 시간과 자원을 사용 |

HotSpot JVM은 일반적으로 **Tiered Compilation(계층형 컴파일)**을 사용한다. 처음에는 인터프리터로 실행하면서 프로파일 정보를 모으고, 실행 빈도에 따라 C1을 거쳐 더 높은 최적화 단계로 이동할 수 있다. 충분히 뜨거운 코드는 C2 컴파일 대상이 될 수 있다.

개념적인 흐름은 다음과 같다.

```text
인터프리터 실행
      |
      v
실행 정보 수집
      |
      v
C1 컴파일
      |
      v
더 많은 프로파일 정보 수집
      |
      v
C2 컴파일 및 고도화된 최적화
```

실제 컴파일 단계와 전환 조건은 JVM 버전, 옵션, 실행 상황에 따라 달라질 수 있다.

## 7. Deoptimization은 왜 발생할까?

JIT는 실행 중 관찰한 정보를 바탕으로 특정 조건이 계속 유지될 것이라고 가정하고 최적화할 수 있다.

예를 들어 어떤 메서드에 항상 특정 클래스의 객체만 전달된다고 관찰했다면, 해당 상황에 유리한 기계어를 생성할 수 있다. 그런데 나중에 다른 클래스의 객체가 전달되면 기존 최적화의 전제가 깨질 수 있다.

이때 JVM은 잘못된 최적화 결과를 계속 사용하지 않고 **Deoptimization(역최적화)**을 수행할 수 있다. 실행 상태를 복구하고 인터프리터 또는 다른 컴파일 단계에서 다시 실행하도록 전환하는 과정이다.

따라서 JIT는 한 번 컴파일하면 영원히 같은 기계어만 사용하는 단순한 구조가 아니다. 실행 상황이 바뀌면 최적화와 역최적화가 일어날 수 있다.

## 8. JIT 컴파일 결과는 어디에 저장될까?

JIT가 생성한 기계어 코드는 JVM의 **Code Cache**에 저장된다. 이후 해당 코드가 다시 실행될 때 컴파일된 코드를 활용할 수 있다.

Code Cache도 JVM이 관리하는 메모리 영역이므로 무한하지 않다. 코드 캐시가 부족해지면 추가적인 JIT 컴파일에 영향을 줄 수 있다. 운영 환경에서 컴파일 관련 로그나 Code Cache 사용량을 확인하는 이유다.

## 9. JIT 동작을 확인하는 방법

JVM 옵션을 이용하면 컴파일 활동을 관찰할 수 있다.

```bash
java -XX:+PrintCompilation Calculator
```

JDK 버전에 따라 지원 옵션과 출력 형식은 달라질 수 있다. 최신 JDK에서는 다음과 같은 통합 로깅 옵션도 활용할 수 있다.

```bash
java -Xlog:jit+compilation=debug Calculator
```

실제 성능 비교를 할 때는 단순히 프로그램을 한 번 실행하고 시간을 재면 안 된다. JVM은 실행 도중 프로파일을 수집하고 JIT 컴파일을 진행하기 때문에 초기 실행과 충분히 워밍업된 실행의 성능이 다를 수 있다.

벤치마크를 작성할 때는 다음 사항을 고려해야 한다.

1. 워밍업 단계와 실제 측정 단계를 구분한다.
2. 여러 번 반복 측정하고 결과의 편차를 확인한다.
3. JVM 실행 옵션과 JDK 버전을 동일하게 맞춘다.
4. 측정 코드가 최적화로 제거되지 않도록 주의한다.
5. 정밀한 Java 마이크로벤치마크에는 JMH를 활용한다.

## 10. 백엔드 서버에서 JIT가 중요한 이유

Spring Boot 기반 서버는 JVM 위에서 실행된다. 서버가 시작된 직후에는 아직 충분한 실행 정보가 쌓이지 않았을 수 있고, 시간이 지나면서 요청이 반복되는 메서드가 JIT 최적화 대상이 될 수 있다.

예를 들어 다음과 같은 서버 기능을 생각해 볼 수 있다.

- 로그인 요청에서 반복 호출되는 인증 로직
- 상품 조회 API의 데이터 가공 로직
- 채팅 메시지를 변환하고 전달하는 로직
- 주문 금액과 할인 금액을 계산하는 로직

이런 코드가 반복 실행되면 JVM은 실행 정보를 수집하고 최적화할 수 있다. 다만 JIT가 있다고 해서 데이터베이스 쿼리, 네트워크 지연, 락 경합 같은 병목까지 해결되는 것은 아니다.

실제 서버 성능을 분석할 때는 다음 항목을 구분해야 한다.

| 성능 요소 | 확인할 내용 |
| --- | --- |
| JIT | 컴파일 활동, 워밍업, Code Cache |
| GC | 객체 할당량, GC 빈도와 정지 시간 |
| CPU | 사용률, 스레드별 CPU 점유 |
| DB | 쿼리 실행 시간, 인덱스, 커넥션 풀 |
| 네트워크 | 외부 호출 시간, 전송 지연 |

JIT는 JVM이 애플리케이션 코드를 효율적으로 실행하도록 돕는 기능이다. 서버 전체 성능은 JIT뿐 아니라 메모리, 스레드, DB, 네트워크가 함께 영향을 준다.

## 핵심 정리

- Java 컴파일러는 `.java` 파일을 JVM 바이트코드인 `.class` 파일로 변환한다.
- JVM은 인터프리터로 바이트코드를 실행하면서 실행 정보를 수집한다.
- 자주 실행되는 코드는 JIT 컴파일러가 기계어로 변환해 실행 효율을 높일 수 있다.
- HotSpot JVM은 C1과 C2, Tiered Compilation을 통해 컴파일과 최적화를 단계적으로 수행할 수 있다.
- 인라이닝, 루프 최적화, 이스케이프 분석 등 다양한 최적화가 가능하다.
- 실행 중 가정이 깨지면 Deoptimization이 발생할 수 있다.
- JVM 성능 측정에서는 워밍업과 반복 측정이 중요하다.
