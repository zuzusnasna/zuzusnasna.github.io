## 1. Java에서도 메모리 누수가 발생할까?

Java는 Garbage Collector가 객체 메모리를 관리하지만 메모리 누수가 발생할 수 있다. 더 이상 업무에 필요하지 않은 객체가 참조 관계 때문에 계속 도달 가능한 상태로 남아 있으면 GC가 회수하지 못한다.

예를 들어 요청이 끝났는데도 static Map에 요청 데이터를 계속 저장한다면 객체는 계속 살아 있을 수 있다. 메모리를 직접 해제하지 않는 언어라고 해서 메모리 누수가 없는 것은 아니다.

## 2. 메모리 누수와 메모리 부족 구분

| 현상 | 의미 |
| --- | --- |
| Memory Leak | 불필요한 객체가 계속 참조되어 회수되지 않음 |
| High Allocation Rate | 객체가 매우 빠르게 생성되어 GC 부담이 커짐 |
| OutOfMemoryError | JVM이 필요한 메모리를 확보하지 못함 |

메모리 사용량이 높다는 사실만으로 누수라고 판단하면 안 된다. 정상적인 캐시나 처리량 증가로 힙 사용량이 높을 수도 있다. GC 이후에도 사용량이 계속 증가하는지, 객체가 의도치 않게 유지되는지 확인해야 한다.

## 3. 자주 발생하는 누수 원인

### Static 컬렉션

```java
class RequestHistory {
    private static final List<String> HISTORY = new ArrayList<>();

    static void add(String request) {
        HISTORY.add(request);
    }
}
```

요청이 들어올 때마다 기록을 추가하고 제거하지 않으면 리스트가 계속 커진다. 최대 보관 개수나 만료 정책을 정해야 한다.

### 캐시 만료 누락

캐시는 조회 성능을 높이지만 만료 정책이 없다면 오래된 데이터까지 계속 보관할 수 있다. 최대 크기, TTL(Time To Live), 제거 정책을 함께 설계해야 한다.

### Listener 해제 누락

객체가 이벤트 리스너로 등록되어 있으면 이벤트 발행자가 해당 객체를 계속 참조할 수 있다. 사용이 끝났을 때 등록 해제 절차가 필요하다.

### ThreadLocal 정리 누락

스레드 풀은 스레드를 재사용한다. 작업이 끝난 뒤 ThreadLocal 값을 제거하지 않으면 다음 작업까지 이전 값이 남을 수 있다.

```java
try {
    requestContext.set(context);
    process();
} finally {
    requestContext.remove();
}
```

## 4. 힙 사용량 관찰

메모리 문제를 분석할 때는 순간적인 사용량보다 시간에 따른 추세를 본다.

- 요청량이 증가할 때만 힙이 증가하는가?
- GC 이후 사용량이 다시 낮아지는가?
- 트래픽이 줄어도 사용량이 유지되는가?
- 특정 객체 타입의 개수가 계속 증가하는가?
- Old 영역에 살아남는 객체가 늘어나는가?

GC 로그와 모니터링 지표를 함께 보면 객체 생성량 증가인지, 회수되지 않는 객체 누적인지 구분하는 데 도움이 된다.

## 5. Heap Dump 수집과 분석

Heap Dump는 특정 시점의 힙 객체와 참조 관계를 기록한 자료다. 운영 환경에서는 덤프 파일이 크고 민감한 데이터가 포함될 수 있으므로 저장 공간과 접근 권한을 고려해야 한다.

실행 중인 JVM에서 수집하는 대표적인 방법은 다음과 같다.

```bash
jcmd <PID> GC.heap_dump /tmp/heap.hprof
```

또는 JVM 실행 옵션으로 OOM 시 덤프를 남길 수 있다.

```bash
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/var/log/app/
```

덤프 분석 도구에서는 다음을 확인한다.

- Histogram: 클래스별 객체 개수와 메모리 크기
- Dominator Tree: 다른 객체를 많이 붙잡고 있는 객체
- Retained Heap: 특정 객체를 제거했을 때 함께 회수될 수 있는 메모리 규모
- Path to GC Roots: 객체가 GC Roots에서 도달 가능한 경로

단순히 가장 큰 객체만 찾기보다 어떤 참조가 객체를 유지시키는지 확인하는 것이 핵심이다.

## 6. 문제를 해결하는 순서

1. 메모리 사용량과 GC 로그를 통해 증가 시점을 확인한다.
2. 동일한 부하 조건에서 재현 가능한지 살펴본다.
3. Heap Dump에서 증가한 객체 유형을 찾는다.
4. GC Roots 참조 경로로 유지 원인을 확인한다.
5. 캐시 만료, 컬렉션 제거, 리스너 해제, ThreadLocal 정리 등을 적용한다.
6. 동일한 부하로 다시 테스트해 힙 사용량이 안정되는지 검증한다.

힙 메모리를 늘리는 것은 일시적인 완화책일 수 있다. 객체가 계속 쌓이는 원인을 제거하지 않으면 더 큰 메모리에서도 문제가 다시 발생한다.

## 7. 백엔드 운영에서의 의미

Spring Boot 서비스에서는 요청 객체, 세션, 캐시, 비동기 작업, 스레드 로컬 문맥 등 다양한 객체가 생성된다. 특히 장시간 실행되는 서버는 작은 누수도 누적될 수 있다.

메모리 문제가 발생하면 애플리케이션 코드뿐 아니라 트래픽 변화, 캐시 정책, 작업 큐 적체, 스레드 풀 상태도 함께 확인해야 한다.

## 핵심 정리

- Java도 참조가 남아 있는 객체 때문에 메모리 누수가 발생한다.
- GC 이후 힙 사용량이 계속 증가하는지 관찰한다.
- Heap Dump에서 Dominator Tree와 GC Roots 경로를 확인한다.
- 캐시·static 컬렉션·리스너·ThreadLocal의 생명 주기를 관리한다.
- 힙 증설보다 객체가 유지되는 근본 원인을 찾는 것이 중요하다.
