EC2에서 애플리케이션을 실행하면서 포트가 이미 사용 중이거나 이전 프로세스가 남아 있는 문제를 여러 번 경험했다.

## 포트를 확인하는 이유

```bash
sudo ss -lntp
```

특정 포트를 누가 사용하고 있는지 확인하면 애플리케이션 문제와 실행 환경 문제를 구분할 수 있다.

## 프로세스 확인

```bash
ps aux | grep java
```

컨테이너 안의 프로세스와 호스트에서 직접 실행한 Java 프로세스가 섞이면 어떤 프로세스가 포트를 점유했는지 헷갈릴 수 있다.

## Docker와 함께 볼 것

```text
호스트 포트
   ↓
Docker port mapping
   ↓
컨테이너 내부 포트
   ↓
Spring Boot
```

호스트의 8080과 컨테이너 내부 8080은 같은 개념이 아니다.

## 배운 점

배포 장애가 발생했을 때 애플리케이션 로그만 보는 것보다 **포트 → 프로세스 → 컨테이너 → 애플리케이션 순서로 범위를 좁혀가는 방식**이 문제 해결에 효과적이었다.

## 더 깊게 이해하기: 포트 충돌은 프로세스와 네트워크 바인딩의 문제다

애플리케이션이 포트를 열려면 해당 주소와 포트를 다른 프로세스가 이미 사용하고 있지 않아야 한다. 서버가 실행되지 않는다면 애플리케이션 로그뿐 아니라 실제로 누가 포트를 점유하고 있는지 확인해야 한다. 프로세스 이름만 보고 종료하면 다른 서비스에 영향을 줄 수 있으므로 PID와 실행 경로를 확인한 뒤 조치한다.

프로세스가 포트를 열고 있어도 외부에서 접근할 수 있다는 보장은 없다. 방화벽, 보안 그룹, 컨테이너 포트 매핑, 리버스 프록시 설정이 별도의 조건으로 작동한다.

### 점검 순서
- 해당 포트를 리슨하는 PID와 프로그램을 확인한다.
- 프로세스가 어떤 명령과 작업 디렉터리로 실행됐는지 확인한다.
- 로컬에서 접속되는지, 외부에서 접속되는지 단계별로 테스트한다.
- 컨테이너 내부 포트와 호스트에 공개한 포트를 구분한다.

포트 문제는 무조건 프로세스를 종료하는 것으로 해결하기보다 서비스의 실제 소유자와 네트워크 경로를 확인해야 한다.
