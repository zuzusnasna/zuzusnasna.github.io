EC2 배포에서 Nginx를 앞단에 두면서 웹 서버와 애플리케이션 서버의 역할을 분리했다.

## 구조

```text
Client
  ↓ 80 / 443
Nginx
  ↓
Spring Boot : 8080
```

Nginx는 외부 요청을 받고 적절한 내부 애플리케이션으로 전달하는 Reverse Proxy 역할을 한다.

## 왜 직접 8080을 열지 않았나

외부에서 애플리케이션 포트에 직접 접근하도록 만들기보다 Nginx가 외부 진입점이 되면 TLS, 정적 파일, 라우팅, 여러 애플리케이션 인스턴스로의 전달 등을 한 곳에서 관리하기 편하다.

## 다중 인스턴스

```text
             Nginx
             /   \
          App1   App2
```

두 인스턴스로 확장하면 Nginx에서 요청을 분산할 수 있다.

## 배운 점

Reverse Proxy는 단순한 포트 전달이 아니라 **외부 트래픽과 내부 애플리케이션을 분리하는 배포 구조의 경계**라고 이해했다.

## 더 깊게 이해하기: 리버스 프록시는 요청 경계와 연결 설정을 담당한다

리버스 프록시는 클라이언트 요청을 받아 내부 애플리케이션으로 전달한다. 이를 통해 외부에 애플리케이션 포트를 직접 공개하지 않고, TLS 종료·도메인 라우팅·정적 파일 처리·로드 밸런싱을 한 지점에서 관리할 수 있다. 다만 프록시를 추가하면 전달 헤더, 타임아웃, WebSocket 업그레이드처럼 별도 설정이 필요하다.

WebSocket은 일반 HTTP 요청과 달리 연결을 업그레이드한 뒤 오래 유지한다. Nginx가 업그레이드 헤더를 전달하지 않거나 타임아웃이 짧으면 연결이 수립되지 않거나 중간에 끊길 수 있다. 따라서 일반 REST API가 정상이라는 사실만으로 WebSocket 프록시도 정상이라고 판단하면 안 된다.

### 설정 검증
- 외부 요청이 올바른 내부 서비스와 포트로 전달되는가?
- 원래 호스트와 클라이언트 IP를 전달하는 헤더를 적절히 처리하는가?
- WebSocket 업그레이드 헤더와 연결 타임아웃을 설정했는가?
- 설정 변경 후 문법 검사와 실제 연결 테스트를 수행하는가?

프록시는 단순히 요청을 전달하는 중간 장치가 아니라 네트워크 경로와 운영 정책을 결정하는 구성 요소다.
