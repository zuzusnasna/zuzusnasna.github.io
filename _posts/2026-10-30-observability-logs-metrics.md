운영 중 문제가 발생했을 때 애플리케이션 로그만 보는 것에는 한계가 있다. 어떤 종류의 정보가 필요한지에 따라 로그와 메트릭을 나눠서 봐야 한다.

## 로그

특정 요청에서 무슨 일이 발생했는지 확인하는 데 적합하다.

```text
2026-10-30 22:10:03 ERROR OrderService - payment failed
```

## 메트릭

시간에 따른 시스템 상태를 숫자로 확인한다.

- CPU
- Memory
- GC
- 요청 수
- 응답 시간
- 오류율
- DB connection pool

## 헬스체크

애플리케이션이 살아 있는지와 주요 의존성이 정상인지 확인한다.

```text
Client / LB
    ↓
/actuator/health
    ↓
Application
```

## 실제 문제 해결 순서

```text
사용자 지연 발생
 ↓
응답 시간 / 오류율 확인
 ↓
CPU / Memory / I/O 확인
 ↓
애플리케이션 로그 확인
 ↓
DB / Redis 확인
```

RealTimeChat에서 높은 Swap과 I/O wait를 먼저 확인했던 것도 이와 같은 접근이었다.

## 배운 점

운영 문제는 로그 한 줄로 찾는 것이 아니라 **시스템 전체에서 어느 계층이 병목인지 범위를 좁혀가는 과정**이다.

## 더 깊게 이해하기: 로그와 메트릭은 서로 다른 질문에 답한다

로그는 특정 요청이나 오류가 어떤 경로로 발생했는지 설명하는 데 유용하고, 메트릭은 시간에 따라 시스템 상태가 어떻게 변하는지 보여준다. 로그만으로는 전체 지연 추세를 보기 어렵고, 메트릭만으로는 특정 요청이 실패한 이유를 찾기 어려울 수 있다. 두 정보를 요청 ID나 시간 범위로 연결하면 원인 분석이 쉬워진다.

관측 지표는 많을수록 좋은 것이 아니다. 서비스 지연 시간, 요청량, 오류율, 자원 사용량처럼 운영 질문에 답하는 핵심 지표부터 정하고, 경보가 실제 조치로 이어지도록 기준을 세워야 한다.

### 운영 관측 점검
- 요청량·오류율·지연 시간의 변화를 함께 볼 수 있는가?
- 로그에서 비밀번호, 토큰, 개인정보가 노출되지 않는가?
- 대시보드가 실제 장애 대응 질문에 답하는가?
- 수집 시스템 자체의 자원 사용량이 작은 서버에 부담을 주지 않는가?

관측 가능성은 대시보드를 설치하는 것으로 끝나지 않는다. 이상 징후를 발견하고 원인 범위를 좁혀 실제 조치로 연결할 수 있어야 한다.
