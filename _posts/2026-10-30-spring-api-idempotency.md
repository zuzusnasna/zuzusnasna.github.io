사용자가 결제 버튼을 빠르게 두 번 누르거나 네트워크 재시도로 같은 요청이 반복되면 서버는 같은 작업을 두 번 처리할 수 있다.

## 멱등성

같은 요청을 여러 번 보내더라도 결과가 한 번 처리한 것과 동일하도록 만드는 성질이다.

```text
Client
 ↓ POST + Idempotency-Key
Server
 ↓
키가 이미 처리됨?
 ├─ Yes → 기존 결과 반환
 └─ No  → 작업 처리 + 결과 저장
```

## 왜 중요한가

결제, 좌석 예약, 주문 생성처럼 중복 처리가 치명적인 API에서는 단순히 버튼을 비활성화하는 것만으로 충분하지 않다. 클라이언트 재시도와 서버 중복 요청까지 고려해야 한다.

## 구현 시 고려할 것

- 요청을 식별할 고유 키
- 키 저장 위치
- 처리 중인 요청의 동시 접근
- 성공 결과 재사용
- 키의 만료 시간

## 배운 점

동시성 문제는 동시에 여러 사용자가 접근하는 경우뿐 아니라 **같은 사용자의 동일 요청이 반복되는 상황**에서도 발생한다는 것을 알게 됐다.

## 더 깊게 이해하기: 멱등성은 재시도 상황에서 중요하다

네트워크 요청은 서버에서 처리되었더라도 응답이 클라이언트에 도착하지 않을 수 있다. 사용자가 다시 요청하거나 브라우저가 재시도하면 같은 업무가 두 번 실행될 위험이 있다. 멱등성은 동일한 요청을 반복해도 업무 결과가 한 번 처리한 것과 같도록 만드는 성질이다.

GET처럼 조회를 위한 요청은 일반적으로 멱등하게 설계하지만, 결제나 예약 같은 POST 요청은 중복 요청을 별도로 통제해야 할 수 있다. Idempotency-Key를 받는다면 키의 유효 범위, 요청 본문이 달라졌을 때의 처리, 결과 보관 기간, 동시 중복 요청의 처리 방법을 정해야 한다.

### 설계 체크리스트
- 중복 요청을 식별할 안정적인 키가 있는가?
- 같은 키의 요청이 동시에 들어와도 한 번만 처리되는가?
- 이전 요청의 결과를 재사용할지 충돌로 응답할지 정의했는가?
- 멱등성 기록과 실제 업무 변경이 원자적으로 처리되는가?

멱등성은 요청이 절대 중복되지 않는다고 가정하는 대신, 중복이 발생해도 데이터가 안전하도록 만드는 설계다.
