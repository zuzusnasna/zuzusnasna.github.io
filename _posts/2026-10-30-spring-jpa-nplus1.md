JPA를 사용할 때 가장 조심해야 하는 문제 중 하나가 N+1이다. 객체 관계를 편하게 조회한 코드가 실제 DB에서는 여러 번의 SELECT로 실행될 수 있다.

## 예시

```java
List<Order> orders = orderRepository.findAll();

for (Order order : orders) {
    order.getMember().getName();
}
```

주문 목록을 한 번 조회한 뒤 각 주문의 회원을 지연 로딩하면 회원 수만큼 추가 쿼리가 실행될 수 있다.

```text
1번 주문 조회
 + 회원 조회
 + 회원 조회
 + 회원 조회
 + ...
```

## 해결 방향

조회 목적에 맞게 fetch join, EntityGraph, DTO projection 등을 검토할 수 있다.

```jpql
select o
from Order o
join fetch o.member
```

## 중요한 점

무조건 모든 연관관계를 EAGER로 바꾸는 것은 해결책이 아니다. 화면에서 실제로 필요한 데이터를 기준으로 조회 전략을 선택해야 한다.

## 배운 점

JPA 코드를 볼 때는 객체 코드만 보면 안 되고 **실제로 몇 개의 SQL이 실행되는지**까지 확인해야 한다.

## 더 깊게 이해하기: N+1은 조회 전략과 화면 요구가 맞지 않을 때 나타난다

N+1 문제는 부모 목록을 조회한 뒤 각 부모의 연관 데이터를 가져오는 과정에서 추가 쿼리가 반복되는 현상이다. 목록이 100개라면 부모 조회 1회 뒤 자식 조회가 100회 발생할 수 있다. 문제는 JPA 자체가 느리다는 것이 아니라 조회 시 필요한 데이터 범위와 로딩 전략이 맞지 않는 데 있다.

Fetch Join은 특정 조회에서 연관 데이터를 함께 가져올 수 있지만, 컬렉션을 여러 개 조인하면 결과 행이 늘어나거나 페이징이 기대와 다르게 동작할 수 있다. EntityGraph, DTO projection, batch size 등 대안도 있지만, 각각의 장단점이 있다.

### 진단 순서
1. SQL 로그나 쿼리 통계로 실제 쿼리 수를 확인한다.
2. 어떤 화면/API가 어떤 필드를 필요로 하는지 정리한다.
3. 조회 조건에 맞춰 Fetch Join 또는 DTO 조회 등을 선택한다.
4. 결과 중복, 페이징, 메모리 사용량을 다시 확인한다.

N+1을 해결할 때는 무조건 모든 연관관계를 EAGER로 바꾸지 않는다. 필요한 조회에서 필요한 데이터만 가져오는 방향이 안전하다.
