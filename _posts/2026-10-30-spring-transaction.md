트랜잭션은 여러 DB 작업을 하나의 업무 단위로 묶어 **중간 상태가 외부에 노출되지 않도록 하는 것**이다.

## 기본 흐름

```text
트랜잭션 시작
 ↓
변경 1
 ↓
변경 2
 ↓
모두 성공 → commit
하나라도 실패 → rollback
```

## 왜 서비스 계층에서 많이 사용하는가

Controller는 HTTP 요청과 응답에 집중하고 Repository는 DB 접근을 담당한다. 여러 Repository 작업을 하나의 업무로 묶어야 할 때 Service에 트랜잭션 경계를 두면 책임이 명확해진다.

## 주의할 점

트랜잭션 안에서 외부 API 호출이나 오래 걸리는 작업을 수행하면 DB 커넥션과 잠금을 오래 유지할 수 있다.

```text
DB 트랜잭션
  ├─ DB 변경
  ├─ 외부 API 호출  ← 오래 걸리면 문제
  └─ DB 변경
```

가능하면 트랜잭션 범위를 실제 데이터 변경에 필요한 만큼 짧게 유지해야 한다.

## 배운 점

`@Transactional`을 메서드 위에 붙이는 것만 외우는 것보다 **어떤 작업을 하나의 원자적인 업무로 묶어야 하는지**를 먼저 판단하는 것이 중요했다.

## 더 깊게 이해하기: 트랜잭션 경계는 업무의 원자성을 표현한다

트랜잭션은 여러 데이터 변경을 하나의 논리적 작업으로 묶는다. 예를 들어 주문 생성과 재고 차감이 함께 성공하거나 함께 취소되어야 한다면 두 작업은 같은 트랜잭션 경계 안에 있어야 한다. 반대로 트랜잭션 범위를 너무 크게 잡으면 잠금이 오래 유지되고 다른 요청이 기다리는 시간이 늘어난다.

Spring의 `@Transactional`은 프록시 기반으로 적용되므로 같은 클래스 내부 호출이나 메서드 접근 범위에 따라 예상과 다르게 동작할 수 있다. 또한 기본 롤백 규칙과 checked exception의 처리 방식을 이해해야 예외가 발생했을 때 데이터가 실제로 롤백되는지 판단할 수 있다.

### 점검할 항목
- 어떤 데이터 변경이 함께 성공해야 하는지 먼저 정의했는가?
- 외부 API 호출처럼 오래 걸리는 작업을 트랜잭션 안에 넣지 않았는가?
- 예외가 발생했을 때 실제 롤백 여부를 테스트했는가?
- 동시 요청에서 잠금 범위와 트랜잭션 시간이 적절한가?

트랜잭션 어노테이션을 붙이는 것보다 어떤 업무 단위를 원자적으로 보장해야 하는지 설명하는 것이 더 중요하다.
