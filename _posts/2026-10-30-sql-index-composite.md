인덱스를 공부하면서 가장 중요한 것은 인덱스 개수가 아니라 **실제 조회 패턴과 실행 계획**이었다.

## 단일 인덱스

```sql
CREATE INDEX idx_member_email ON member(email);
```

자주 특정 이메일로 조회한다면 효과가 있을 수 있다.

## 복합 인덱스

```sql
CREATE INDEX idx_order_member_status
ON orders(member_id, status);
```

여러 컬럼을 함께 조건으로 사용하는 경우 고려할 수 있다.

## 순서가 중요한 이유

복합 인덱스는 컬럼 순서에 따라 활용 방식이 달라진다. 따라서 단순히 WHERE에 등장하는 컬럼을 모두 넣는 것이 아니라 **선택도, 정렬, 범위 조건, 실제 쿼리 패턴**을 같이 봐야 한다.

## 실행 계획

인덱스를 추가한 뒤에는 실제 실행 계획과 실행 시간을 확인해야 한다.

```sql
EXPLAIN SELECT * FROM orders
WHERE member_id = 10 AND status = 'PAID';
```

## 배운 점

튜닝은 "인덱스를 추가하자"가 아니라 **왜 느린지 측정하고 실행 계획을 확인한 뒤 필요한 변경만 하는 과정**이다.

## 더 깊게 이해하기: 복합 인덱스는 컬럼 순서가 중요하다

복합 인덱스는 여러 컬럼을 하나의 인덱스 키로 구성한다. 일반적으로 선두 컬럼을 조건으로 사용하지 않으면 인덱스의 효율적인 탐색 범위를 활용하지 못할 수 있다. 따라서 컬럼 순서는 단순히 선택도가 높은 컬럼을 앞에 두는 규칙 하나로 결정하지 않고, 실제 WHERE 조건, 조인, 정렬 패턴과 함께 판단해야 한다.

예를 들어 `(room_id, created_at)` 인덱스는 특정 방의 메시지를 시간 순으로 조회하는 패턴에 도움이 될 수 있다. 반면 전체 방에서 특정 시각 이후 메시지를 조회하는 쿼리에는 같은 효율을 보장하지 않는다. 실제 실행 계획과 데이터 분포를 확인해야 한다.

### 인덱스 검토 순서
- 자주 실행되는 쿼리와 조건을 수집한다.
- 인덱스의 선두 컬럼이 쿼리 조건과 맞는지 확인한다.
- 정렬과 범위 조건을 포함한 실행 계획을 확인한다.
- 인덱스 추가 후 INSERT·UPDATE 비용과 저장 공간도 살펴본다.

인덱스는 많을수록 좋은 것이 아니라 읽기 비용을 줄이는 이득이 쓰기와 저장 비용보다 큰 경우에 도입하는 구조다.
