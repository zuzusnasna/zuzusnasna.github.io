새 팀 프로젝트 아이디어를 정리하면서 단순 CRUD 서비스보다 **개발자가 DB나 코드를 변경했을 때 성능이 나빠졌는지 자동으로 확인하는 시스템**을 설계했다.

## 문제

개발 환경에서는 데이터가 적어서 쿼리가 빠르지만 실제 운영 규모의 데이터에서는 갑자기 느려질 수 있다.

```text
코드 변경
   ↓
SQL 변경
   ↓
대량 데이터에서 성능 저하
   ↓
운영에서 발견
```

이 문제를 배포 전에 발견하는 것이 목표다.

## 기본 구조

```text
React
 ↓
Spring Boot API
 ↓
Test Runner
 ↓
MySQL 테스트 DB
 ↓
실행 계획 / 실행 시간 수집
 ↓
이전 결과와 비교
```

## 핵심 기능

- 테스트용 대량 데이터 생성
- 기준 쿼리 등록
- 변경 후 쿼리 실행
- 실행 시간 측정
- `EXPLAIN` 기반 실행 계획 비교
- 이전 결과 대비 성능 회귀 판정
- 결과 이력 관리

## 중요한 설계 기준

성능이 10% 느려졌다고 무조건 실패로 볼 수는 없다. 실행 환경의 편차가 있기 때문에 여러 번 실행하고 기준값과 비교하는 방식이 필요하다.

## 배운 점

성능 개선을 사람이 직접 하는 것이 아니라 **성능 저하를 자동으로 발견할 수 있게 만드는 것**도 백엔드 시스템의 중요한 역할이 될 수 있다는 방향으로 설계를 시작했다.

## 설계 문서에서 더 구체화할 결정

성능 회귀 자동 검증 플랫폼을 만들려면 테스트 대상 SQL을 안전하게 실행하는 격리 경계가 필요하다. 사용자가 등록한 SQL을 운영 데이터베이스에서 그대로 실행하면 데이터 변경이나 과도한 쿼리로 위험을 만들 수 있다. 따라서 테스트 전용 DB, 제한된 권한, 실행 시간 제한, 데이터 초기화 전략을 먼저 정해야 한다.

성능 비교 결과도 단순한 pass/fail로 끝내기 어렵다. 기준선과 현재 결과를 비교할 때 실행 환경과 데이터셋 버전이 다르면 결과의 신뢰도가 떨어진다. 실행 시간뿐 아니라 실행 계획, 처리 행 수, 오류, 반복 측정의 분산을 함께 저장하면 원인 분석에 도움이 된다.

### MVP 범위 제안
1. 읽기 전용 SQL을 등록하고 테스트 데이터셋을 고정한다.
2. 동일 조건에서 여러 번 실행해 시간과 실행 계획을 수집한다.
3. 기준선과 비교해 경고를 만들되, 측정 편차가 큰 경우에는 자동 실패 대신 검토 상태로 분류한다.
4. 각 실행 결과를 재현할 수 있도록 DB 버전과 설정을 함께 기록한다.

가장 어려운 문제는 실행 버튼이 아니라 측정의 공정성, SQL 실행의 안전성, 결과를 설명할 수 있는 데이터 모델이다.
