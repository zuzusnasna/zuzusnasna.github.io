## 네트워크에서는 같은 요청이 반복될 수 있다

클라이언트가 주문 생성 요청을 보냈는데 응답을 받기 전에 연결이 끊겼다고 가정한다. 서버는 이미 주문을 생성했을 수 있다. 클라이언트가 재시도하면 동일 주문이 두 번 만들어질 위험이 있다.

멱등성은 같은 요청을 여러 번 처리해도 서버의 최종 상태가 한 번 처리한 것과 같도록 만드는 성질이다.

## HTTP 메서드와 멱등성

GET, PUT, DELETE는 HTTP 의미상 멱등하게 설계된다. POST는 일반적으로 멱등하지 않지만, 결제·주문 API에서는 Idempotency-Key를 이용해 중복 처리를 막을 수 있다.

## Idempotency-Key 흐름

1. 클라이언트가 요청마다 고유 키를 생성한다.
2. 서버는 사용자와 키 조합을 기준으로 처리 이력을 확인한다.
3. 처음 보는 키라면 처리 상태를 기록하고 업무를 수행한다.
4. 같은 키의 요청이 다시 오면 기존 처리 결과를 반환한다.
5. 같은 키에 다른 요청 본문이 들어오면 충돌로 거부한다.

키 저장과 업무 데이터 저장은 원자성이 중요하다. DB 트랜잭션과 유니크 제약 조건을 이용해 동시에 들어온 요청 중 하나만 처리되게 설계할 수 있다.

## 동시 요청 경쟁 조건

애플리케이션에서 먼저 조회한 뒤 저장하는 코드만으로는 동시 요청을 막지 못한다. 두 요청이 동시에 키가 없음을 확인할 수 있기 때문이다. DB Unique Constraint, 원자적 INSERT, 적절한 잠금 등을 사용해 최종 중복을 방지한다.

## 운영 고려사항

- 키의 유효 기간과 보관 정책을 정한다.
- 사용자·API 단위로 키 범위를 제한한다.
- 처리 중 상태와 완료 상태를 구분한다.
- 동일 키의 요청 본문이 같은지 검증한다.
- 실패한 요청을 재시도할 수 있는 기준을 정의한다.

**정리:** API 재시도는 클라이언트의 편의 기능이 아니라 서버 데이터 정합성과 연결된다. 주문·결제처럼 중복 실행의 비용이 큰 작업은 멱등성 설계를 고려해야 한다.
