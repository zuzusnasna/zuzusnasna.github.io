## 테스트를 계층으로 나누는 이유

테스트는 많이 작성하는 것보다 실패 원인을 빠르게 찾고 반복 실행할 수 있게 구성하는 것이 중요하다. 테스트 피라미드는 빠르고 격리된 단위 테스트를 중심에 두고, MVC 슬라이스 테스트와 통합 테스트를 필요한 경계에 배치하는 방식이다.

- 단위 테스트: 작은 로직과 클래스의 동작 검증
- 슬라이스 테스트: MVC, JPA 등 특정 계층의 Spring 구성 검증
- 통합 테스트: 여러 Bean과 인프라 연결 검증
- 인수 테스트: 사용자 관점의 주요 시나리오 검증

## JUnit 5 기본

```java
class PriceCalculatorTest {
    @Test
    void appliesDiscount() {
        PriceCalculator calculator = new PriceCalculator();

        int result = calculator.calculate(10_000, 10);

        assertEquals(9_000, result);
    }
}
```

테스트 이름은 조건과 기대 결과를 드러내는 편이 좋다. Given-When-Then 구조로 초기 상태, 실행 동작, 결과 검증을 나누면 테스트 의도를 읽기 쉬워진다.

## 좋은 테스트의 조건

1. 독립 실행 가능하고 실행 순서에 의존하지 않는다.
2. 같은 조건에서 반복 실행해도 결과가 같다.
3. 실패했을 때 원인을 좁힐 수 있다.
4. 내부 구현보다 외부에서 관찰 가능한 동작을 검증한다.
5. 경계값, 예외, 권한, 동시 요청 등 실제 장애 가능성이 높은 조건을 포함한다.

현재 시각, 랜덤 값, 외부 네트워크, 공유 DB 데이터에 의존하면 간헐적 실패가 발생하기 쉽다. Clock 주입, 고정 테스트 데이터, 격리된 DB 등을 활용한다.

## 커버리지의 함정

라인 커버리지가 높다고 업무 규칙이 제대로 검증되었다는 뜻은 아니다. 주문 생성이라면 성공 경로뿐 아니라 재고 부족, 중복 요청, 결제 실패, 권한 부족도 확인해야 한다.

**실무 기준:** 테스트는 구현을 따라가는 코드가 아니라 변경 후에도 핵심 동작이 유지된다는 근거다.
