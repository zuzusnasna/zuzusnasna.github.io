외부 대중교통 API를 연결하면서 가장 어려웠던 부분은 API를 호출하는 것 자체가 아니라 **외부 데이터 형식을 우리 서비스에서 사용할 수 있는 형태로 바꾸는 것**이었다.

## 외부 API와 내부 모델

외부 API의 응답을 Controller에서 그대로 화면에 전달하면 외부 시스템의 구조가 우리 서비스에 그대로 노출된다.

```text
External API
   ↓
Response DTO
   ↓
Service 변환
   ↓
Domain 형태
   ↓
React
```

이렇게 중간 변환 계층을 두면 외부 API가 바뀌어도 내부 코드의 영향을 줄일 수 있다.

## 막차 문제

첫 번째 지하철 노선의 막차를 탈 수 있다고 전체 귀가가 가능한 것은 아니었다.

```text
A역
 ↓ 1호선 막차
환승역
 ↓
2호선 막차 종료
 ↓
실제 귀가 불가
```

따라서 전체 경로를 단순 문자열로 판단하지 않고 구간별 도착 시간과 다음 환승 가능 여부를 확인해야 했다.

## Redis 캐시

같은 경로를 반복해서 요청하면 외부 API 호출 비용이 커질 수 있어 Redis를 사용했다. 다만 캐시된 데이터가 항상 최신이라는 보장은 없기 때문에 새로고침이나 기준 변경에서는 최신 데이터를 다시 확인하도록 했다.

## 배운 점

외부 API 프로젝트에서는 **API 호출 코드보다 데이터 정규화와 실패 상황을 고려한 도메인 설계**가 더 중요할 수 있다는 것을 배웠다.

## 외부 서비스 연동을 기능 경계로 분리하기

지도·교통 API는 내부 서비스가 통제할 수 없는 응답 지연과 호출 제한을 가진다. 외부 API 호출을 도메인 로직 여러 곳에서 직접 수행하면 응답 형식 변경이나 인증 방식 변경이 전체 코드로 퍼질 수 있다. 연동 전용 서비스와 응답 DTO를 두고, 외부 응답을 내부 모델로 변환하면 변경 범위를 좁힐 수 있다.

특히 위치와 경로 데이터는 좌표계, 시간 단위, 환승 구간, 운행 시간 같은 의미가 정확해야 한다. 응답에 값이 있다는 이유로 바로 화면에 보여주지 말고 누락된 필드, 비정상 좌표, 만료된 경로 정보를 검증해야 한다.

### 장애와 제한 처리
- 타임아웃과 호출 제한을 처리한다.
- 재시도 가능한 오류와 즉시 실패해야 하는 오류를 구분한다.
- 외부 API가 실패해도 이미 저장된 모임 정보까지 사용할 수 있도록 분리한다.
- API 키와 사용자 위치 같은 민감한 값을 로그에 노출하지 않는다.

외부 연동의 완성도는 정상 응답 화면뿐 아니라 외부 시스템이 느리거나 중단되었을 때 서비스가 얼마나 안전하게 동작하는지로 판단해야 한다.


## 경로 판정은 응답 표시와 별도로 검증한다

외부 API에서 경로를 받아왔다는 것과 그 경로를 사용자가 실제로 이용할 수 있다는 것은 다른 판단이다. 첫 번째 노선의 막차가 남아 있어도 환승역에 도착했을 때 다음 노선의 운행이 끝났다면 전체 귀가 경로는 성립하지 않는다. 따라서 경로를 구간별로 나누고, 각 구간의 도착 시각과 다음 구간의 출발 가능 여부를 확인해야 한다.

이런 규칙을 Controller에 직접 넣기보다 서비스 계층에서 판단하도록 분리하면 API 응답 형식과 업무 규칙을 따로 테스트할 수 있다. 외부 API가 반환한 필드가 달라져도 내부 서비스가 사용하는 값으로 변환하는 지점만 수정하면 되기 때문이다.

~~~java
// 구조를 설명하기 위한 축약 예시이며 실제 클래스명은 아님
ExternalRouteResponse response = routeClient.search(request);
RouteResult route = routeMapper.toResult(response);
return routeValidator.validateTransferTimes(route);
~~~

## 캐시를 쓸 때 함께 정해야 하는 것

Redis 캐시는 동일한 경로를 반복 조회할 때 외부 API 호출 수를 줄이는 데 도움이 된다. 하지만 캐시 키에 출발지·도착지·검색 조건이 충분히 반영되지 않으면 서로 다른 요청이 같은 캐시 값을 사용하게 될 수 있다. 캐시 만료 정책이 없다면 오래된 운행 정보가 계속 남을 수 있다.

따라서 캐시를 적용할 때는 다음을 같이 확인해야 한다.

- 요청 조건이 캐시 키에 빠짐없이 반영되는가?
- 운행 시간처럼 변경 가능한 데이터의 유효 기간을 정했는가?
- 캐시 미스와 외부 API 오류를 구분하는가?
- 외부 API가 실패했을 때 사용자에게 보여줄 대체 응답이 있는가?

캐시 적용 여부만으로 성능 개선을 단정하지 않고, 외부 호출 수와 응답 시간, 데이터 최신성을 함께 비교해야 한다.
